> 素材：`Data/正射影像/松山湖-广医大_二维正射_2025-03-13.zip`（1.19 GB）

> 环境限制：**没有 GDAL / rasterio / pyproj**（只有 numpy + Pillow），所以全部手写。

## 二、正射影像的技术参数（实测）

```
尺寸        39658 × 46163  = 18.3 亿像素
波段/位深   RGBA，8 位/通道
压缩        Adobe Deflate（zlib）
分块        256 × 256，共 28055 块   ← 关键
Predictor   1（无水平差分，解压后直接用）
坐标系      EPSG:32649 = WGS 84 / UTM zone 49N（投影坐标，单位米）
像素尺寸    0.0464 m  →  4.64 cm/px
左上角      UTM (793143.593, 2539712.925)
NODATA      alpha=0（RGBA 的 alpha 通道）
```

空三报告里的指标：

```
average GSD        0.0512 m
flying altitude    131.3 m
images             181 张
coverage area      0.50 km²
georef RMSE        0.489 m
```

### 地理范围（自己用 UTM 反算）

```
包围盒   lat 22.9202018 ~ 22.9398509
        lng 113.8579506 ~ 113.8762816
尺寸     1840 m × 2142 m
中心     lat 22.9300263, lng 113.8671161
```

⚠️ **包围盒 ≠ 实际覆盖**。实测**NODATA 约 87%** —— 这条航线拍的是**斜向的狭长走廊**
（约 200 m 宽 × 2.5 km 长），与报告的 `coverage area 0.50 km²` 吻合。
所以贴上地图后是一块**斜向长条**，不是矩形。**这是正常的**（Terra 按航线覆盖裁边）。

另外：它与现有 `test` 项目的数据**相距 27.4 km**（是另一个片区）。

## 三、关键验证 ①：没有 GDAL，也能按块随机读

这是整个方案能不能成立的前提 —— 整幅读进内存要 `39658×46163×4 ≈ 7.3 GB`，不可能。

**做法**：解析 TIFF 的 `TileOffsets(324)` / `TileByteCounts(325)` 两个数组，
按需 seek + `zlib.decompress` 单块。

**实测结果**：

```
TileOffsets     28055 项（与 155×181 块布局完全吻合）
单块解压        正好 262144 B = 256×256×4 RGBA
耗时            0.0 ~ 0.7 ms / 块
Predictor       1（无需还原差分）
```

**同时验证了反面**：用 `PIL.crop()` 取 256×256 要 **6.4 秒** ——
说明 Pillow 会整幅解码，**不能拿它做瓦片服务**。必须走手工按块读。

## 四、关键验证 ②：投影正确

没有 `pyproj`，所以 UTM 与 WGS84 之间的正/反算都是**手写的横轴墨卡托公式**。

**用"网格收敛角"验证**（一个只依赖几何的独立判据）：

```
实测：向东 1000 m 在经纬度平面上抬高 −1.13°
理论：Δλ · sin(φ) = (113.87° − 111°) × sin(22.93°) = 1.12°
```

**两者吻合到 0.01°** —— 说明投影公式实现正确。

## 五、关键验证 ③：真的能生成正确的 Web 瓦片

管线：

```
Web 瓦片 (z,x,y) 的像素
  → 经纬度            （Web Mercator 逆算）
  → UTM 49N 东/北      （手写横轴墨卡托正算）
  → 源图像素           （GeoTIFF 的 ModelPixelScale + ModelTiepoint）
  → 从对应 256×256 块采样
```

**输出肉眼确认**：道路笔直、车道线清晰、车辆是正常比例（z18 下 5 m 的车约 9 px，
与 0.55 m/px 吻合），无拉伸、无错位。斜向是**真实地理走向**（一条 NE–SW 的路
+ 1.13° 的网格收敛），不是投影错误。

## 六、性能，和一个必须解决的架构问题

同一层级连渲染 5 块（第 1 块含预热）：

| 层级 | 分辨率 | 稳态中位 | 一块瓦片要读几个源块 |
|---|---|---|---|
| z17 | 1.10 m/px | **560 ms** | 数百 |
| z18 | 0.55 m/px | 161 ms | 约 140 |
| z19 | 0.27 m/px | 73 ms | **44** |
| z20 | 0.14 m/px | 38 ms | 约 9 |

**反直觉但讲得通**：**粗层级反而更慢**。因为 z17 的一块瓦片覆盖 281 m 地面，
而一个源块只有 256 × 4.64 cm = 11.9 m —— 要翻几百个源块，却只从中采几个点。
细层级反过来：一块瓦片只碰 9 个源块。

**修法（已验证）**：预先生成**一级总览**，粗层级读总览、细层级读原图。

```
建 1/8 总览：跨步读 418 个源块，0.33 s
产出：608×704 px，2.97 m/px，约 2 MB
```

更进一步：1/8 抽样但**读全部源块**可得 0.37 m/px 总览
（约 4957×5770 = 28.6 Mpx ≈ 114 MB），一次构建约 8~9 s，
即可覆盖 z ≤ 18 全部粗层级；z19+ 仍读原图（73 ms，配 LRU 缓存可接受）。

## 七、附带收获：DSM 能解决一个已知局限

```
dsm.tif  19829 × 23082（1/2 分辨率，0.0928 m/px）
         单波段 float32，分块 256×256，同坐标系 EPSG:32649
         NODATA = -9999
         实测有值区域高程 28 ~ 34 m（松山湖一带，合理）
```

这直接对应之前记录的**覆盖几何局限**：

> `rel_alt` 是相对**起飞点**的高度，而覆盖圆环半径要的是**离地高度 AGL**。
> 山顶起飞飞到侧下方时 `rel_alt` 为负会被跳过（实测 `贡嘎 …075758_0001_D`
> 有 20% 帧因此被跳）。正确做法需要 **DEM**。

有了 DSM/DTM 就能算 `AGL = abs_alt − 地面高程(该点)`，这个局限可以真正修掉。

⚠️ 注意 **DSM 是"表面"**（含植被/建筑），算 AGL 严格说该用 **DTM**（裸地）。
DJI Terra 两个都能出；用 DSM 会略微低估离地高度。作为"比没有强"的改进是够的。

## 八、可行性与代价结论

### 可行（已验证）

| 环节 | 状态 |
|---|---|
| 读 GeoTIFF 地理参考 | ✅ 手写解析 IFD，拿到 scale/tiepoint/EPSG |
| 按块随机读 | ✅ 0.7 ms/块，内存可控 |
| UTM ↔ WGS84 | ✅ 手写，网格收敛角验证到 0.01° |
| 生成 Web 瓦片 | ✅ 几何肉眼确认正确 |
| 预览/总览 | ✅ 已跑通 |

### 代价与风险

1. **EPSG 只覆盖 UTM/WGS84**。这个是 32649；若拿到 Beijing54 / Xian80 /
   CGCS2000 高斯投影的成果，椭球与带号规则不同，公式要扩。
   **建议**：从 GeoKeyDirectory 读 EPSG，只支持 WGS84 系（326xx / 327xx）；
   遇到别的就**明确报错**，不要静默算错。
2. **必须做缓存**。一块 38~161 ms，平移时会同时请求十几块 ——
   不做 LRU/磁盘缓存会明显卡。
3. **必须预建总览**，否则粗层级 560 ms/块。
4. **采样现在是最近邻**，成品应换双线性（否则斜向边缘有锯齿）。
5. **磁盘**：一个 795 MB 的 tif + 约 114 MB 总览缓存；多个正射会累积。
6. **DSM 计算 AGL** 是另一件事，工作量独立（要按点查高程 + 改覆盖几何）。

### 建议的实现顺序

```
① 最小可用：只读总览（0.37 m/px）当一张覆盖层贴上去
   —— 不计金字塔、不支持深度缩放，几小时可完成，能立刻"看见"正射影像
② 完整：按需瓦片服务 /ortho/{z}/{x}/{y}.png + LRU 缓存 + 预建总览
③ 进阶：DSM 查高程 → 修掉覆盖几何的 AGL 局限
```
