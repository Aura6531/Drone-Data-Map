# 「这个位置被哪些画面拍到过」—— 跨架次取证检索（图墙）

> 需求（用户 2026-10-13）：
> **在地图上选点后，搜索此位置曾经被包含的巡查画面和对应帧，可以找到很多个结果、
> 包括多个架次的，出现多个图排列起来，然后我点哪个图就跳转到对应的视频文件对应位置，
> 时间一样是往前倒数 3 秒，播放到那一刻自动停止。**

---

### 三档检索（用户 2026-10-13 提出）

用户原话：

> **「应该给个检索选项，只看最清晰的 1 张，还是检索所有飞机不同角度和位置上，
> 对那个点拍摄到的多个图。可以按照最清晰的来排序，但你要知道，地面是有遮挡物的，
> 可能刚好最清晰的照片中，想看的东西在树的背后，而另一张没那么清晰的照片
> 从另一个角度拍到了。」**

这段话点出一个容易被忽略的事实：**"最清晰"和"最有用"不是一回事**。
树/楼会挡住 —— 最清晰的那张可能正好在遮挡物后面，而另一张从别的方向看过去恰好没被挡。

所以做成**三档**，而不是"1 张 / 全部"两档：

| 档位 | 给什么 | 什么时候用 |
|---|---|---|
| `Clearest only` | 全场最清晰的 **1** 张 | 只想知道"看得最清是什么样" |
| `Every pass` | **每个独立趟次 1 张**（该趟最清的那帧） | 想知道这块地被拍过几次 |
| `Different angles` ★默认 | **每种视角 1 张**（方位/俯角接近的合并，只留最清的） | **找"换个角度还能不能看到"** |

`Different angles` 的做法：

1. 按清晰度从好到差扫
2. 一条只有在「与已选中的每一条都明显不同视角」时才入选
3. 视角差判据：方位角差 ≥ **25°** 或 俯角差 ≥ **12°**（`FIND_ANGLE_*_DEG`）

这样既保证**第一张是最清晰的**，又保证后面每张都带来**一个新的观察方向** ——
正是为了绕开遮挡。

**方位角必须用「无人机 → 目标」算，不能用 `frame_yaw`** —— 云台会独立转动，
`frame_yaw` 是相机指向、不一定对着目标。新增 `coverage.bearing_elevation()`。
（`yaw` 的约定实测确认过：`yaw=0` 时足迹中心在正北、`yaw=90` 在正东。）

| # | 架次 | 帧 | cm/px | 方位角 | 俯仰角 | 在哪些档 |
|---|---|---:|---:|---:|---:|---|
| 1 | 095258 | 11597 | **4.8** | 272.9° | −46.1° | 三档都有 |
| 2 | 101516 | 5565 | 5.2 | 25.1° | −24.4° | 三档都有 |
| 3 | 101516 | 11878 | 9.7 | 136.6° | −12.7° | 三档都有 |
| 4 | 095258 | 10475 | 13.5 | 23.2° | −14.8° | 与 #2 同视角 → 被合并 |
| 5 | 101516 | 4021 | 17.4 | 161.4° | −7.0° | 与 #3 同视角 → 被合并 |
| 6 | 095258 | 0 | 18.5 | 48.1° | −2.1° | 三档都有 |
| 7 | 101516 | 11363 | 22.1 | 195.6° | −5.6° | 三档都有 |

- `Clearest only` → **1** 条
- `Every pass` → **7** 条
- `Different angles` → **5** 条（#4、#5 各与一条已有视角重合）
- `passes_total` 始终是 7，前端据此说"只显示了 N / 共 M 趟"

## 位置：挂在**右栏视频下面**（2026-10-13 改）
图墙原先挂在中栏地图下面。问题是中栏被**地图 + 覆盖面板 + 点位详情**挤满了，
图墙出来之后**滚不到、看不到** —— 用户原话：

> **「Frames of this spot 的检索结果框可以放到右下角，不然太挤了我看不到，红框这个区域。」**

现在挂在右栏、视频面板下方：

```
右栏（.col-right，flex column）
  ├─ 视频面板（flex:0 0 auto —— 按内容高度）
  ├─ 照片展示区（有照片时才占位）
  └─ 图墙（flex:1 1 auto —— 吃掉视频剩下的高度，内部滚动）★
```

三点理由：

1. 它本来就是"点一张图 → 跳到对应视频时刻"，**跟视频同一栏最顺手**
2. 中栏那段挤满了，放那儿等于看不见
3. 视频面板是"按内容高度"的，**剩下的高度正好让图墙自己滚**

样式上要**覆盖掉中栏那套** `max-height:430px`（那是为"挤在地图下方"定的），
否则右栏下面还是空一块：

```css
.col-right .frame-gallery{flex:1 1 auto;min-height:200px;max-height:none;margin-top:0;
                          display:flex;flex-direction:column}
.col-right .frame-gallery .grid{flex:1 1 auto;min-height:0;overflow:auto;
                                align-content:start;padding-right:2px}
```

卡片区自己滚（不是整个框滚）—— 这样**标题和「更多」按钮始终可见**，
不会因为卡片多就被顶出视野。

> 这类"东西在、但看不见"的问题**不会报错**，所以专门加了
> `test_gallery_slot.js` 钉住：元素只存在一个、确实在 `colRight` 之内、
> 不在中栏、`flex:1` 与 `overflow:auto` 都在。

## 〇、它和已有功能的关系

| | 原有 `Find flights at this position` | 本次新增 `Frames of this spot` |
|---|---|---|
| 检索范围 | **单个架次内**（A+B 正反投影） | **整个项目所有架次**（查覆盖栅格） |
| 依据 | 画面中心 / 可见性反投影 | 「这一格有没有被拍到、多清」 |
| 结果 | 一条条文本结果 | **图墙**：缩略图 + 元信息，按清晰度排序 |
| 跳播 | 跳到视频某一刻 | 同样，**倒数 3 秒 + 到点自动停** |

新功能不是替换，而是**换个问法**：

> 原来问「哪一趟飞过这里」；现在问「这块地，历史上被拍成过什么样」。

这个差别在实测里很直观（见第四节）：同一片地，一趟是正下视 31 m（**1.1 cm/px**），
另一趟是路对面 61 m 浅俯角（**3.8 cm/px**）—— 差 3.5 倍。图墙把两张摆在一起，
哪张能用一眼就看出来了。

## 二、实现要点

### 检索：遍历覆盖网格，而不是遍历轨迹点

对项目里**每个已建好的覆盖网格**做一次点查询（O(1)）：

```
cell_of(lat,lng) -> count>0 ? -> frame_at_min 给出「看得最清的那一帧」
                              -> gsd_best_map 给出「有多清」
```

比遍历所有轨迹点快得多，而且直接复用已经验证过的数据。
**没建覆盖网格的架次会被明确跳过并说明原因**（前端把原因显示出来），
而不是悄悄少给结果。

### 排序：按解像度从好到差

需求是"找到那些画面"，但人的实际诉求是**先看最清楚的那张**。
所以按 `ground_m_per_px` 升序 —— 检索结果的第一张就是最有判读价值的。

### 去重：每张卡 = 一个**独立趟次**（2026-10-13 修，用户当场发现）

**原来的做法是错的。** 它按「同一视频 + 时间差 < 0.15 s」合并，
但更早一步就已经**每个架次只保留 GSD 最好的那一帧**了 —— 所以一个架次最多出一条。

用户选中一个位置后立刻发现：

> **「我当前选择的这个位置，应该有多次拍到，为什么结果只出来一个？」**

原因是同一架次会**来回飞好几趟**，每趟的高度、俯角、清晰度都不同 ——
那正是要找的"不同画面"。实测那个点：

```
架次 095258：1211 帧拍到 → 4 个独立趟次
  趟1 帧0     18.5 cm/px  高19.6  俯角-17°   ← 起飞段
  趟2 帧6791   106 cm/px   高100   俯角-2°    ← 几乎平视
  趟3 帧10476 13.5 cm/px  高99.5  俯角-31°
  趟4 帧11597  4.8 cm/px  高99.7  俯角-23°   ← 最清

架次 101516：1196 帧拍到 → 9 个独立趟次
```

**一共 13 个不同画面，原来只显示 1 条。**

现在的规则：

1. 扫出**所有**真的把这点看在画面里的帧（不再只挑最优）
2. 按时间间隔分组：相邻命中帧隔 **> 8 s**（`FIND_PASS_GAP_SECONDS`）算**另一趟**
3. **每趟给一条** —— 该趟里 GSD 最好的那一帧
4. 相邻两趟再近于 **5 s**（`FIND_DEDUP_SECONDS`）的只留最清的一条
   （避免把一次连续观察切成两张几乎一样的卡）

新增字段：`pass_seconds`（本趟看着这点多久）、`pass_frames`（本趟拍到几帧）、
`passes_total`（去重前的总趟数）。前端副标题与卡片相应改口径：

```
Across 2 flight(s), 7 separate pass(es) saw this position
· best frame of each pass · sorted by how clearly (best first) · 3.3s
```

卡片上多一行 `this pass 23.7s` —— **用来区分"专程拍"和"路过扫到"**。

修后同一个点的结果：

| # | 架次 | 帧 | 时刻 | cm/px | 高度 | 俯角 | 本趟 |
|---|---|---:|---:|---:|---:|---:|---:|
| 1 | 095258 | 11597 | 1159.7s | **4.8** | 99.7 | −23.0° | 23.7s |
| 2 | 101516 | 5565 | 556.5s | 5.2 | 61.6 | −31.2° | 35.9s |
| 3 | 101516 | 11878 | 1187.8s | 9.7 | 61.7 | −31.8° | 2.9s |
| 4 | 095258 | 10475 | 1047.5s | 13.5 | 99.5 | −31.4° | 30.0s |
| 5 | 101516 | 4021 | 402.1s | 17.4 | 61.1 | −30.1° | 28.8s |
| 6 | 095258 | 0 | 0.0s | 18.5 | 19.6 | −17.4° | 5.0s |
| 7 | 101516 | 11363 | 1136.3s | 22.1 | 61.8 | −25.2° | 8.5s |

**1 条 → 7 条**，清晰度跨 **4.8 ~ 22.1 cm/px（4.6 倍）**，俯角跨 −17°~−32°。

> 为什么是 7 条而不是手工按帧统计的 13 趟：`find_frames` 里还有一道
> **足迹包围盒预筛**，会把"收口帧里目标其实落在远处"的帧排掉（那部分本来就不可靠）。
> 逐层数据：`网格说 540 帧覆盖 → 包围盒 881 → 射影确认 590 帧 → 3 趟`。
> **7 条是正确结果**，不是漏了 6 条。


### 缩略图：ffmpeg 抽帧 + 磁盘缓存

- 抽帧走 `ffmpeg -ss <t> -frames:v 1 -vf scale=W:-2`，先出 PNG 再让 Pillow 转 JPEG
- 缓存 key = `sha1(视频路径 | 时间 | 宽度)`，落在**视频同目录的 `.thumbs/`**
- **实测：冷启 2.3 s，缓存命中 0.02 s** —— 所以缓存是必须的
- 前端做**懒加载**（进入视口才取图）+ 同时最多 3 个请求：
  一屏几十张如果同时打过去，每张各起一个 ffmpeg，服务会被打满

### 跳播：复用「点照片跳视频」那条链路

`jumpToFrameHit()` 拼一个和 `jumpToPhotoVideo()` 一样的载荷，交给 `openVideoFromPopup()`：

```js
{ folder_index, relative_path, video_start: start_seconds,
  video_end: 0, photo_pause_at: target, video: video_name }
```

于是**转码兜底、2 倍速、地图跟随、倒数 3-2-1、到点自动暂停全部自动继承**，
一行都不用重写。

> ⚠️ **这里踩过一个坑**：`photo_pause_at` 一开始写的是
> `from < target ? target : 0`（照抄照片跳转的写法）。
> 那在"这一帧就在视频开头"（`from === 0`）时会设成 **0 = 不暂停** ——
> 于是一路播下去，**停不在用户要看的那一帧上**。
> 而需求是"播到那一刻自动停止"，所以改成**只要有目标时刻就一定停**：
> `photo_pause_at: target`。
> 倒计时显示与否由播放器按剩余量自己决定（剩余不足 1 秒就不显示数字）。
>
> 照片那条链路保持原样没动 —— 它的语义是"看按下快门前后"，
> 没有余量时不停是合理的；帧检索的语义是"看那一帧"，必须停。

## 三、界面与交互

### 选点规则（用户 2026-10-13 定的）

> **无论视频是否在播放，点击之后就是新的点**，然后就可以按新位置去搜索；
> **但直到点开对应帧的照片画面，才会更换右侧播放的视频内容。**

所以：

| 动作 | 选点 | 检索结果（图墙） | 右侧播放的视频 |
|---|---|---|---|
| 点地图（**视频开着也照点**） | **变成新点** | **清空**（旧结果配新坐标会误导） | **不动** |
| 点 `Find flights at this position` | 不变 | 按新点重查 | 不动 |
| 点 `Frames of this spot` | 不变 | 按新点出新图墙 | 不动 |
| **点图墙里的某一张** | 不变 | 不变 | **这时才换** |
| 点 `Clear selection` | 清空 | 清空 | 不动 |

配套的两处改动：

- **去掉了**原来"视频开着就拦住地图点击"的限制
  （那句 `While the video is open, clicking the map does not change the selection.`
  已经不存在了）
- **视频开着时不自动 `fitBounds`**：加载覆盖图层会把地图跳到覆盖区，
  但你正在对照画面，跳走会打断 —— 图层照样加载，等你关掉视频或自己平移过去就能看到

### 图墙长什么样

```

┌──────────────┐ ┌──────────────┐
```

这正是这个功能要解决的问题。

```
缩略图 JPEG + 缓存命中更快 / 网格外 0 命中 / max_gsd 过滤 / 参数校验
```

### 前端测试（`test_frames_ui.js`）

用**合成检索结果**驱动页面，像用户一样点按钮，然后读回真实渲染结果：

```
页面脚本不抛异常 / 没选点时不发请求 / 图墙打开 /
拿到 3 条命中并渲染 3 张卡 / 标题与统计文案 /
缩略图 URL 的 folder_index、path、t 逐个对（含跨架次那条）/
卡片提示里的起播与暂停时刻 /
点图后读**真实的 clip** 核对：架次、视频文件、起播时刻、到点暂停时刻 /
「到点自动暂停」机制接上了（且没留下"余量不足就不暂停"的老写法）/
起播余量不足时也停在那一帧 /
换选点：图墙清掉、选点换成新的、**播放内容不变** /
只有点开某一帧才换播放内容 /
清空后页面状态回到空 / 0 命中时讲清原因
                                        全部通过
```

> 写这个测试时的三个教训：
>
> ① DOM 桩的 `innerHTML` 如果只当字符串存，`querySelector('h4')` 永远取不到 ——
> **那验的就不是页面而是桩**。给桩补了一个极简 HTML 解析器。
>
> ② 桩的 `getElementById` 会返回脱离文档后仍被缓存的那一份，所以 DOM 层的
> "清空了没有"判断不可靠，改成用**页面自己的状态**（`frameGalleryHits`/`frameGalleryShown`）。
>
> ③ **页面里取网格和测试里读网格必须用同一种查法**（都用 `document.getElementById`），
> 否则一个用 `querySelector('.grid')`、一个用 `getElementById`，
> 桩会造出两个子元素实例，出现"一边看到有卡、另一边看到空"的假象。

## 五、性能

| 环节 | 实测 |
|---|---|
| 检索（2 个网格） | **0.6 s** |
| 缩略图首次 | 2.3 s / 张（ffmpeg 抽帧，走磁盘缓存） |
| 缩略图缓存命中 | **0.02 s** / 张 |

**已知不足**：冷缓存时一屏 12 张要 12 次 ffmpeg 抽帧（前端限流 3 并发，
所以约 4 轮 ≈ 10 s 才铺满）。可以改进的方向：

- 抽帧时用 `-ss` 放在 `-i` 前（已这样做）配合更小的 `-probesize`，还能再快一些
- 或者建覆盖网格时**顺便预抽**每个"格子代表帧"的缩略图（代价是建网格变慢）
- 或者后端做一个小并发池，一次请求返回多张拼图

目前先按需加载 —— 用户往往是看前几张就决定了。
