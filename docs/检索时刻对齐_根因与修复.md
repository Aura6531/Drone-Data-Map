# 检索结果"对不准点位"的真正根因（2026-10-13，已修）

> 用户反复报过三次：
> **「这个图真的有包含我点的点吗？确认是否算法有误」**
> **「之前那个对不准点位的情况还存在……差了多远，不可能拍到的啊。应该是算错了？」**
>
> **用户是对的。** 我前两次核完都说"算法正确"，那两次都错了。
> 这篇记录真正的根因、证据链，以及为什么前两次会判断错。

---

## 一、根因：把「遥测采样下标」当成了「视频帧号」

```
覆盖网格里 frame_at_min / frame_alt / frame_pitch / … 的下标
   是**抽稀后的遥测采样点序号**（30fps 每 3 帧一个点 -> 10 Hz，约 12453 个）

而 times[] 也是按采样点存的，它就是 SRT 的 cue 时间（与视频时间轴一致）

但 find_frames 里写的是：
    target_seconds = frame_index * TELEMETRY_STEP / 30.0
                     = frame_index / 10
    ^ 这等于假设"采样下标 ÷ 10 = 秒"，也就是假设采样间隔**严格** 0.1 s
```

`times[]` 的实际间隔**不是**严格 0.1 s —— 真实 SRT 的 cue 时间戳在 0.031~0.035 s
之间抖动，抽稀后平均约 0.1014 s。于是这个折算**越到后段越偏**：

| 采样下标 | `÷10` 算出的时刻 | `times[]` 的真实时刻 | 偏差 |
|---:|---:|---:|---:|
| 0 | 0.000 s | 0.000 s | 0 s |
| 11793 | 1179.300 s | **1196.996 s** | **17.7 s** |

**17.7 秒 × 约 13 m/s ≈ 230 m** —— 正好是地图上"差了几百米"的量级。

> 为什么这个 bug 特别隐蔽：采样数组长度（12453）比出问题的下标（11793）只大一点，
> **不越界、不报错**，只是悄悄取到了 17.7 秒之后的坐标。
> 而视频跳播用的 `frame` 号又是**对的**（缩略图看起来没问题），
> 所以症状只表现为"地图上的位置不对"。

## 二、证据链：用画面里 DJI 烧录的 OSD 定案

**OSD 是唯一能"从视频内部"验证坐标的东西。** 把原帧左上角放大 5 倍读出来：

```
视频 19:39.300（帧 11793）的 OSD：
    2026-09-24 10:34:56
    23.054897°N 114.108218°E 75.486m
```

再到 SRT 里按时间戳反查：

| 候选 | cue 时间 | 坐标 | 与 OSD 距离 |
|---|---:|---|---:|
| 行 34847（cue 1179.28 s） | 1179.28 s | 23.054897, 114.108218 | **0.0 m** ✓ |
| 行 35379（代码原来取的） | 1197.00 s | 23.053181, 114.106496 | 228 m ✗ |

**行 34847 = 采样下标 11616**（11616 × 3 = 34848），而代码取的是采样下标 **11793**。
差 177 个采样 ≈ 17.7 s ≈ 228 m。**与 OSD 完全对得上 —— 定案。**

> 另一个交叉验证：`find_frames` 报告 `alt=61.7 m, pitch=-26.9°`，
> 而帧 11793 处 SRT 的 **绝对**高是 75.486 m（相对高 61.7 m + 起飞点高程 13.8 m），
> 数字自洽 —— 说明几何用的是**正确的采样点**，只有"下标 → 秒"这一处错了。

## 三、修法

### 1. `times[]` 成为唯一权威时刻来源

```python
# coverage_api.find_frames
t = float(times[r["fi"]])          # 而不是 r["fi"] * step / 30
target = float(times[fi])
```

### 2. 把换算收成一处，别再手写

```python
# coverage.py
VIDEO_FPS = 30.0

def telemetry_sample_of_frame(frame_index):
    """视频帧号 -> 抽稀后的遥测采样下标。整个模块唯一的换算入口。"""
    return int(round(frame_index * TELEMETRY_STEP / VIDEO_FPS))

def video_seconds_of_frame(frame_index):
    """视频帧号 -> 视频内秒数。同样只此一处。"""
    return frame_index * TELEMETRY_STEP / VIDEO_FPS
```

### 3. 网格自带逐采样点时刻（`frame_times`）

新建网格时把 `times` 抄进 `frame_times[]` 一起存盘（float64）。
`CoverageGrid.frame_time(i)` 优先用它；旧网格没有这个字段才退回按帧率折算
（会偏，但至少不崩）。**实测这比"每次查询都去读 SRT"更可靠也更快。**

### 4. 前端不再自己算

后端新增 `player_seek_seconds`（= 该采样点的 cue 时间，与 `target_seconds` 同一把尺子）。
`jumpToFrameHit()` 改成**只用后端给的秒数**，删掉任何"帧号 → 秒"的换算。

## 五、我为什么前两次判断错了（值得记的教训）

| 我做的核对 | 得出的（错误）结论 | 漏了什么 |
|---|---|---|
| 用**存储的** `frame_alt/pitch` 重算足迹，看目标在不在画面内 | "在画面内，算法正确" | 存储值本身是用**同一个错下标**取的，**自证循环** |
| 把目标投回**用同一个错下标**抽出来的帧 | "十字落在预期地物上" | 同上 —— 抽帧用的是错的时刻，等于拿错帧验证错下标 |

**共同错误：所有验证都用同一个（错误的）时间来源。**
真正跳出来的那一步是引入了**外部真值** —— 画面里 DJI 烧录的 OSD 经纬度。
它不依赖我的任何换算，所以能把整个链条钉住。

> **教训**：闭环验证只有"所有环节同源"时才有效；
> 怀疑对象是"时间对齐"时，必须引入**时间之外**的独立真值
> （画面里的 OSD、地物、另一份日志）。

## 六、回归测试

`test_coverage.py` 第 7 节：

```
建网格时把 times 抄进了 frame_times
frame_time 用 frame_times 的值（而不是按帧率折算）
按帧率折算会算成另一回事（正是那个 bug）
视频帧号 300（10 s）-> 采样下标 30（10Hz）
视频帧号 11793（19:39.3）-> 采样下标 1179，不是 11793
```

最后一条是**反例断言**：如果有人把 `fi * step / 30` 那套写法搬回来，它会立刻失败。
