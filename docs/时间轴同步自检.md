# 视频 / 航迹 时间轴同步自检

> 用户 2026-10-14 要求：
> 「要加文件校验，至少视频文件时长和 geojson 的时长是需要对应的，发现不同步就弹框
> 让重新生成 srt 和 geojson 等后续文件，**不要平移**，因为可能不只是裁切开头和结尾，
> 飞行时信号卡一下，中间的片段就会呆住，这些都有可能被裁掉。」

---

## 一、要解决的问题：时间轴被**非均匀**破坏

这个程序从导入到检索，整条链路都假设一个前提：

> **SRT 时刻 == 视频时刻，1:1。**

依据在代码里能直接看到 —— `video_start` 就是 SRT cue 的起始时间戳
（`project_manager.parse_dji_srt`），航迹里的 `point_times` 直接抄它，
覆盖网格的 `frame_times` 也抄它。

在程序之外裁过视频之后，这个前提就破了。实测后果（用 600 s 那段素材算的）：

| 裁掉 | 画面 / 检索 / 缩略图 | 地图上的无人机标记 |
|---:|---|---:|
| 10 s | 画面**晚 10 s** | 偏 **116 m** |
| 30 s | 晚 30 s | 偏 **323 m** |
| 60 s | 晚 60 s | 偏 **261 m** |
| 120 s | 晚 120 s | 偏 **404 m** |
| 300 s | 晚 300 s | 偏 **1336 m** |

偏差量**恒定**（等于裁掉的秒数），不随播放进度增大。

**最要命的是它是静默的**：跳错时刻、抽错帧、标记飘走，界面上没有任何提示。

### 哪些检测**抓不到**它

| 机制 | 为什么抓不到 |
|---|---|
| 覆盖网格的 `is_stale()` | 只比 **SRT 的 mtime**（`coverage_api` 第 129 行）。不动 SRT 它就认为网格有效 |
| 航迹 `.geojson` | 导入时生成，与视频之间**没有任何指纹绑定** |
| 缩略图缓存 | key 只有 `(路径, 秒数, 宽度)`（第 559 行），**没有文件指纹** → 旧的错图会一直命中 |
| 转码片段缓存 | ✅ **这个反而是安全的** —— key 含 `st_size + st_mtime`，会自动失效 |

我静态核查了三个模块，"同一行里同时出现 `duration` 与 `srt`"的次数是 **0** ——
从来没有把视频时长和 SRT 时间跨度对过。

## 二、为什么**不做**"平移时间戳"

因为破坏**不一定是均匀的**。用户点出的正是这个：

> 「飞行时信号卡一下，中间的片段就会呆住，这些都有可能被裁掉。」

如果中间被挖掉一段，那么**这段之前**偏 N 秒、**这段之后**偏 M 秒 ——
时间轴被分成了两段，任何**单一偏移量**都修不好。

所以校验只负责**报告**，修复动作是**重新生成**：从**新视频**里重新抽 SRT，
才能得到与它自洽的时间轴。

（也因此程序里**没有**任何"整体偏移 SRT 时间戳"的功能，这是刻意的。）

## 三、实现了什么

### 后端

| 位置 | 内容 |
|---|---|
| `project_manager.check_project_sync()` | 逐条比对：视频真实时长 vs 航迹（或 SRT）记录的时长 |
| `project_manager._track_duration_of_geojson()` | 从航迹里读时长。**两种写法都要认**：单 feature + `point_times` 数组；多 feature 各自带时长 |
| `project_manager._srt_duration()` | SRT 的时间跨度 |
| `project_manager.resync_existing_files()` | 就地重生成 SRT + 航迹 + 清缓存 |
| `GET /api/project/sync-check?name=&tolerance=` | 自检接口 |
| `GET /api/project/sync-fix?name=&folder_index=&relative_path=` | 修复接口 |

**参照物优先级**：有航迹就用航迹，没有就用 SRT（360 素材就是这种：
它没有也不该有 `.geojson`，位置来自 SRT）。

**容差 ±2.0 s**（`SYNC_TOLERANCE_SECONDS`）。为什么不是 0：SRT 的最后一个 cue
与视频最后一帧本来就不完全重合 —— 实测两段 360 素材差 **0.03 s / 0.31 s**。
而"裁掉一段"至少也是零点几秒起步，2 s 既能滤掉正常抖动、又能抓住有实际影响的不同步。

### 前端

| 位置 | 内容 |
|---|---|
| `#syncModal` | 真正的模态框（盖全屏 + 背景模糊）。配色沿用页面既有红系 |
| `showTimelineSync()` | 列出每条问题的视频名、时长差、两个时长、参照文件名 |
| `rebuildSyncedFiles()` | 逐条重生成，**实时打印进度**；失败项单独列出并给出「该怎么办」 |
| `checkTimelineSync()` | 进页面 + 换项目时各跑一次 |

为什么做成**模态**而不是一行提示：这是**静默的错**，不挡住用户根本不会注意到。

## 四、一个必须说清的**局限**

重生成的前提是"能从视频里重新抽出遥测"。DJI 把遥测放在视频的**字幕流**里，
所以这一步是否可行，取决于视频是怎么裁的。实测：

```
原视频        字幕流 1 个  ['mov_text']
ffmpeg -c copy 裁过的   字幕流 0 个  []          ← 字幕流丢了
```

**字幕流丢了就抽不出来**，而这恰恰是最常见的裁法。这种情况下程序**无法**自动算出
正确的时刻 —— 因为正确的时刻只存在于**被裁之前的原始视频**里，程序看不到它。

所以修复失败时，界面**明确说清**这一点并给出可行的下一步
（用导出该视频的原始 App 重新导出一次、勾选保留字幕、放进同一文件夹再重建），
而不是给一句含糊的报错。

> **踩过的坑**：第一版在 SRT 抽取失败时**仍然**用旧 SRT 重建了航迹 ——
> 结果 `record_count` 一个都没变、时长还是 1228.66 s、自检依然报错。
> 用户看到 "track rebuilt" 却什么都没修好，**比不修更糟**。
> 现在抽取失败就**立刻返回**，不再往下走。

## 五、实测证据

### 单纯自检（`test_sync_check.py`，已登记进 `run_tests.js`）

自建临时项目，故意把航迹时长改短 40 s：

```
[OK] 报出 1 条 error -> 1
[OK] 参照物是**航迹**（不是 SRT） -> track
[OK] 差 40 s 被算对（delta = 参照 − 视频，航迹改短所以是负的） -> -40.0
[OK] 方向判定为 track_shorter -> track_shorter
     message: 视频时长 1228.7 s，但 航迹 记录的时长是 1188.7 s（差 -40.0 s）。
[OK] 只有 SRT 且 SRT 与视频一致 -> 不报错
[OK] SRT 被截短 -> 报 1 条 error -> 1
[OK] 参照物是 SRT -> srt
[OK] 容差 200 s 时不报 -> problems=0
```

## 六、开发中踩的三个坑（都写进注释了）

| 坑 | 症状 | 原因 |
|---|---|---|
| **注释里写了字面量 `</script>`** | 脚本块在那里被**提前截断** —— 第一次整个脚本块语法错，第二次 `initTimelineSyncUI` 的定义整个掉到 HTML 里（表现为下拉框空白、地图不出） | 浏览器解析 HTML 时的硬规则，不是 JS 的规则。**这个坑我踩了两次** |
| **初始化跑得太早** | 自检**永远不弹框**，看起来"没问题" | `loadProjects()` 是异步的且没 await，而 `checkTimelineSync` 里 `if(!projectSelect.value)return` 直接早退。另外弹框 HTML 排在脚本块之后，脚本顶层执行时元素还不存在 |
| **抽取失败还继续往下做** | 用户看到 "track rebuilt" 但自检依然报错 | 用旧 SRT 重建了航迹。应该立刻返回 |

## 七、还没做的（已知）

- **只能检出"时长对不上"**。如果裁掉的片段恰好让总时长保持不变（比如去头 30 s、
  补尾 30 s），这个检查抓不到。要抓那种情况需要比对**视频帧与遥测的对应关系**
  （例如用画面特征），成本高得多 —— 目前没做。
- **不会自动重跑覆盖网格**。SRT 重写后 `is_stale()` 会因为 mtime 变化判定过期，
  但需要用户去覆盖面板点一次重建（或等它按需重建）。
- **缩略图缓存是整体清掉的**（清空该视频目录下所有 `t_*.jpg`），没有做得更精细。
