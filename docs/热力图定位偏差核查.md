# 热力图定位核查（2026-10-13）

> 起因（用户）：
> **「这次检查看到你的热力图在地图上位置向北偏移了几百米的样子，注意检查。」**

## 一、查出并修掉的真 bug：前端用了**过期的网格摘要**

### 问题

`coverageShow()` 里算热力图范围用的是 `coverageCurrentItem().summary`，
而这个 `summary` 来自 `coverageItems` —— **面板打开那一刻抓的一份快照**。

```js
const it = coverageCurrentItem();                    // ← 快照
const bounds = coverageBoundsFromSummary(it.summary);  // ← 用旧范围定位新图
```

后端重建网格之后（或换了机器、别人重建过），页面不刷新就会：

> **用旧网格的范围去贴新网格的图** —— 图照样画出来，只是位置不对。

### 差多少（实测）

以 `DJI_...101516` 为例，重建前后：

| | 网格尺寸 | 覆盖面积 |
|---|---|---|
| 重建前 | 1730 × 1730 | 203 公顷 |
| 重建后 | 3122 × 3621 | 590 公顷 |

若仍用旧尺寸定位：

```
东界会少 1891 m，北界会少 1392 m    ← 整块图往西南缩
```

### 修法

`coverageShow()` 开头先向服务端**重取**一次摘要：

```js
await coverageRefreshSummary(it);   // 换成服务端当前那份
```

- 顺手把整份清单也更新（`coverageItems = items`）
- **取不到时退回旧快照** —— 宁可位置旧一点，也好过什么都不显示

### 为什么这类 bug 特别值得记

它**不报错、不崩、图也照画**。唯一迹象就是"看起来歪了几百米"。
要不是你去核对地图，它会一直错下去。

## 二、核对结果：**定位公式本身是正确的**

修完之后我用工具逐项核对（`Code/coverage_bounds_check.py`）：

```
网格 DJI_20260924101516_0001_V.1e221f57.npz
  摘要: grid=[ny=3122, nx=3621]  origin=[23.0408911, 114.0863999]  cell=1.0
  载入: g.ny=3122 g.nx=3621（与摘要一致）
  网格真实范围 : lat 23.0408911..23.0691343   lng 114.0863999..114.1217476
  前端算的范围 : lat 23.0408911..23.0691343   lng 114.0863999..114.1217476
  差（米）     : 纬度 +0.000   经度 +0.000   <- 一致
```

**两个网格都是 0.000 m 差。** 逐个排除：

| 可疑点 | 结论 |
|---|---|
| 原点语义（中心 vs 西南角） | **不是** —— 南界/西界正好等于 origin |
| 换算常数（米/度） | **不是** —— 两边都是 110540 / 111320，逐位相同 |
| 网格尺寸（ny/nx） | **不是** —— 载入值与摘要一致 |
| 覆盖格与航线的关系 | **正常** —— 航线 e 785..2926 / n 690..2513；覆盖格 e 120..3498 / n 120..3000，即每边比航线多约 700 m 的足迹扫掠 |

> 顺带说清一个容易误判的点：**航线在网格里本来就是偏的**（比如第一趟覆盖格 n 120..3000，
> 而航线只占 n 690..2513）。因为网格要装下"航线 + 足迹扫掠到的地面"，
> 不是只装航线。**看到热力图相对航线偏，未必是错。**

## 三、还需要你确认的（我给不出结论的部分）

**定位公式对了，不代表你在屏幕上看到的一定对。** 还有两个可能，需要你帮忙区分：

### 可能 A：底图与航迹之间的配准差

不同底图（天地图矢量 / 天地图影像 / OSM）本身就有**几米到几十米**的配准差。

**判断方法**：切换 `Base map` 下拉框（Street ↔ Satellite ↔ OSM），看偏移是否跟着变。
**如果跟着变 → 是底图的问题，不是我们的图层。**

### 可能 B：仍有别的地方用了旧数据

我修的是"热力图范围"这一条链。如果换了架次之后还歪，可能是别处也缓存了。

**判断方法**：**Ctrl+F5 硬刷新**再试一次。如果刷新后就对齐了 → 就是缓存类问题，
告诉我还剩哪一步会歪，我顺着那条链再查。

### 一个更有说服力的核对法

把热力图和**航迹线**放一起看（它们同源，歪了必然是代码问题）：

1. 先 `Load all tracks` 把航迹画出来
2. 再 `Coverage → Show`
3. 看热力图的颜色区是否**压着**航迹线
   - 压着 → 对齐正确（航迹线本身就是"飞机飞过的地方"，必然被拍到）
   - 整体偏了一段 → 还有问题，把截图发我

## 四、新增测试 `test_coverage_bounds.js`

正因为这类 bug 不能靠"跑起来看看"发现，专门钉住：

```
页面脚本不抛异常 /
换算常数与 Python 侧一致（110540 / 111320）/
范围 = 西南角 + 尺寸（南界 = origin 纬度、西界 = origin 经度）/
南北跨度 = 行数、东西跨度 = 列数，且两轴不同（矩形不是方形）/
**面板打开时拿旧摘要 -> Show 之后必须换成服务端当前的摘要** /
叠加范围用的是新网格宽度（旧的只有 1730）/
取不到服务端摘要时不抛异常、退回旧快照
                                        全部通过
```

第 5 条是关键：用一个"先给旧、再给新"的假清单，
断言 `coverageShow()` 之后用的是**新**那份。

## 五、留下的工具

```bash
cd Code

```

对每个网格打印：

- 摘要里的 `grid` / `origin` / `cell`，以及载入后的 `g.ny`/`g.nx`（应当一致）
- **网格真实范围** 与 **前端算出的范围**，以及差多少米
- 覆盖格的行列范围、是否顶到边界
- **四个方向的实测覆盖点经纬度** —— 在界面上点它们，应正好落在热力图有颜色的边缘

> 提示：工具里 `iy` 是**向北**增长的（ENU 约定），`iy` 小 = 南。
