## 一、读取能力：两份素材的字段逐项对照

| SRT 字段 | M4T（可见光/红外） | **Avata 360** | 解析器取到？ |
|---|:---:|:---:|:---:|
| `latitude` / `longitude` | ✓ | ✓（室内全 0） | ✓ → `recs[].latitude/longitude` |
| `rel_alt` | ✓ | ✓ | ✓ → `alt` |
| `abs_alt` | ✓ | ✓ | 未取（`abs_alt − rel_alt` = 起飞点高程，只在建网格时用一次） |

| `dzoom_ratio` | ✓ | **✗ 没有** | ✓ → `dzoom` |

## 三、必须提前知道的限制：360 素材**没有朝向信息**

`gb_yaw` / `gb_pitch` 在 Avata 360 的 SRT 里**一个都没有**（全文扫过，连 `gimbal` 字样都没有）。
这不是 bug，是 360 全景的特性 —— 它把整个球面都录下来了，"朝向"不是它记录的参数。

**影响：把全景摆到地图上时，需要自己定"哪边是北"。** 三条可走的路：

| 办法 | 说明 |
|---|---|
| **用航迹推** | 起飞后由相邻定位点算航向。悬停/微动时航向噪声大，但飞行段可用 |
| **地面控制点** | 拿一张底图，人工（或自动特征匹配）对两三个地物定北 |
| **退而求其次** | 只做"以该点为心"的俯视视角，不追求绝对朝向 |

**只有高度参与几何这一点反而是好消息**（见下）。

## 四、360 的几何：比针孔**更简单**，且不依赖朝向

等距柱状（equirectangular）的映射是：

```
列号 → 方位角 ψ = (col/W)·360° − 180°
行号 → 仰角 θ = 90° − (row/H)·180°
```

所以**仰角只由行号决定、与偏航无关**，地面距离直接可得：

```
地面距离 d = h / tan(θ)        （θ 为俯角，向下为正）
```

一帧覆盖的地面是**一个圆环**，不是梯形：

- 外半径 = `h / tan(θ_nearest)`，`θ_nearest` = 画面下边缘对应的俯角
- 内半径 = `h / tan(θ_farthest)`，`θ_farthest` = 画面上边缘对应的俯角
- 若相机沿某个方向俯仰，正下方会出现**盲区**（内半径 = `h·tan(俯角)`）

**关键：`h` 和行号就够定地面环，不需要 `gb_yaw`/`gb_pitch`。**
所以现有的 `frame_footprint()`（针孔四角）**完全不适用**，需要另写一族
`equirect_footprint(h, θ_top, θ_bottom)`，但推导是初等的。

> 前提：`.OSV` 是**等距柱状**。目前抽帧看是**单个圆形鱼眼**（3840×3840 里一个圆），
> 而 `.LRF` 是**双鱼眼**（两个圆并排）。这两者的几何不一样，外出前最好定下来。
> 确认方法：把 `.OSV` 的两路流各抽一帧对比，或看它是不是 2:1。

## 五、明天外出拍摄：建议顺便确认这几件事

1. **SRT 里经纬度非零**（`GPSStatus: A`）—— 这是能不能接进地图的前提
2. **采样频率**：本次 1580 行 / 26.36 s ≈ 60 Hz（一帧一条）。
   若飞 10 分钟就是 ~36000 行，抽稀后 ~12000 点，与 M4T 同量级，处理链路不用改
3. **`.OSV` 到底是哪种投影**（等距柱状 / 单鱼眼 / 双鱼眼）—— 决定用哪套几何
4. **有没有航向可推**：起飞后直线飞一段，航迹方向就是航向

## 六、代码侧现状（结论：不用为 360 改读取链）

- `parse_dji_srt()` / `load_srt_telemetry()` 对缺字段**返回 `None` 而不是报错** —— 已验证
- `SRT_FIELD_RES` 里的正则对 360 的字段名同样匹配（`rel_alt` 在，`focal_len` 不在则 `None`）
- 网格构建遇到 `yaw/pitch` 为 `None` 的帧会**跳过**（`frames_skipped`），不会崩
- 所以：**明天的室外 360 素材可以直接 `Build`，只是"覆盖几何"那一步需要新的 360 函数**
