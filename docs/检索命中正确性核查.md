# 检索命中的正确性核查（2026-10-13）

> 起因（用户）：**「frame of this spot 里面的检索结果，这个图真的有包含我点的点吗？
> 确认是否算法有误，变焦镜头，但是根本没对到我点的点上面去啊？」**

结论先说：**你点的那两个命中都是对的**；但顺着这个问题查出了一个**真 bug**，
它在**收口帧**上会让命中偏掉（实测 26% 的收口帧命中，目标其实在画面之外）。

---

## 一、先回答你的问题：你那两条命中是对的

用两条独立证据核对：

**证据 ① 几何重算（不看存储值，从 SRT 重算）**

| 命中 | 无人机水平距离 | 俯角 | 在足迹内 | 距边界 | 记录解像度 vs 独立算 |
|---|---:|---:|---|---:|---|
| 帧 12157 | **1.9 m**（在点正上方） | −90.0° | ✓ | 12.4 m | 0.0106 vs 0.0106 |
| 帧 12452 | 89.6 m | −52.6° | ✓ | 21.4 m | 0.0376 vs 0.0375 |

**证据 ② 把点投影回原帧、画十字**（新增工具 `Code/coverage_check_hit.py`）

- **帧 12157**：十字落在画面中心偏左 → 路边停车带/绿化带。图上 DJI 烧录的 OSD 写着
  `23.047507 N 114.104711 E 42.309 m`，与几何计算吻合。
- **帧 12452**：十字落在画面顶部中间的沙地。OSD 写着
  `23.048688 N 114.104075 E 72.803 m`，同样吻合。

两帧的目标归一化图像坐标分别是 `(−0.06, −0.09)` 和 `(−0.11, +0.75)` —— 都在画面内。

**关于「变焦镜头」**：那一帧实际用的是 **24 mm 广角（`focal_mm: 24.0`）**。
你在播放器里看到的 `Lens Mid tele 3.8×` 是**当时播放位置**的镜头信息，
不是这一帧的 —— 两者不同步，容易误读。

## 二、但确实查出一个真 bug：收口帧的足迹是错的

### 怎么发现的

写了个对照脚本：一帧的足迹范围里随机抽样，分别用
**① 栅格化用的四角连线判定** 和 **② 真实的射影投影**（把点投到图像看 `|xi|,|yi| ≤ 1`）
判定，数不一致的比例。

### 结果（很干净）

| 俯角 | clipped | 四边形多算 | 四边形漏算 |
|---:|---|---:|---:|
| −90.0° | 否 | **0%** | **0%** |
| −32.4° | 否 | **0%** | **0%** |
| **−23.3°** | **是** | **11.7%** | **13.0%** |

**四角连线在非收口帧上是精确的。** 问题只出在**收口帧**。

### 全项目量化（抽检命中）

```
收口帧  : 177 抽检，目标不在画面内  46 (26.0%)
非收口帧: 125 抽检，目标不在画面内   0 ( 0.0%)
```

最严重的偏离到 `max|xi| = 1.40`（画面外 40% 的视场半径）。
全都是 **−21° ~ −24°、clipped=True**。

### 根因

收口（`CLIP_PER_ALT = 12×高度`）的做法是：把远边的**两个角沿径向缩到同一距离**。

```python
p = (q[0] * clip / dd, q[1] * clip / dd)      # 沿各自方向缩到 clip
```

两个角的方向不同 → 缩完落在一条**圆弧**上，而不是一条直线。
于是"远边"从一条直线变成了一段弧，**四边形被扭成了跟真实足迹无关的形状**。

浅俯角时远边本身很长（−23° 时真实远角在 1000 m 开外），收口幅度大，扭曲也最大。

> **线索**：我早先的验证脚本报的"差异"都集中在 `0.4%` 以内（那是正常的边界格溢出），
> 但那次抽样恰好没撞上收口帧。**这次是因为要回答"图里到底有没有那个点"，
> 换了个更严的判据（射影 vs 四边形），才把它暴露出来。**

## 三、影响范围（要说清）

| 场景 | 是否受影响 |
|---|---|
| 「Frames of this spot」在**非收口帧**上的命中 | **不受影响**（0% 误差） |
| 「Frames of this spot」在**收口帧**上的命中 | **可能偏**（26% 的收口帧命中，目标在画面外） |
| 你的两个命中 | **不受影响**（都是非收口帧） |
| 覆盖面积（热力图） | 受影响很小 —— 只在收口帧的远端边缘差几个百分点 |
| 置信度 | 收口帧本来就被 `r_clip` 打了折，方向是对的 |

**哪些架次容易碰到**：俯角小于约 25°、且高度较高的。你的主力俯角是 −30°（不受影响），
但扫视段有 −21°~−24° 的帧，那些会带上这个误差。

## 四、修法 A：查询时按真实射影过滤（**已实施**）

### 改了什么

`coverage_api.find_frames()` 不再"只查 `frame_at_min` 那一帧"，而是：

1. **扫该架次的全部帧**
2. 先用**足迹包围盒**便宜地预筛
3. 用**精确射影**（`coverage.ground_point_in_frame`：把目标投到画面，
   `|xi| ≤ 1` 且 `|yi| ≤ 1` 才算真的拍到）确认
4. 在所有确认的帧里挑**GSD 最好**的那一帧

新增返回值：

| 字段 | 含义 |
|---|---|
| `image_xy` | 目标在该帧画面里的归一化坐标（−1..1），前端可用来画准星 |
| `clipped_frame` | 该帧是否用了收口 |
| `covered_but_not_in_frame` | 网格说"覆盖过"、但**没有任何一帧真的把这点看在画面里**的架次 |

最后那条很重要：以前这种情况会**硬拿一帧充数**，现在**如实说明**。

### 效果（实测）

抽 52 个已覆盖的格，逐点跑一遍 `find_frames`：

```
命中条目里的「画面外」条数: 0      （修复前收口帧上是 26%）
一个命中都没有的点: 0 / 52
总用时 134.6s，平均每点 2.6 s
```

对用户点的那一点，答案**没有变**（还是 12157 / 12452 —— 那两帧本来就在画面内），
但**边界情况不再给出错的结果**了。

### 代价

平均 **2.6 秒/次**（两个架次、约 1.9 万帧）。比原来"直接查一格"慢，但：
- 检索本来就要覆盖多个架次，这点延迟可以接受
- 换来的是"结果一定真的包含你点的点"

> **试过但撤回的优化**：用"目标方位/俯仰与相机姿态对比"做预筛，理论更快。
> 但**符号极易搞反** —— `ang` 是仰角（正），`pit` 是俯角（负），
> 夹角应当是 `|ang + pit|` 而不是 `|ang − pit|`。我第一版写成了相减，
> 结果命中的帧全变了（12065/7412 而不是 12157/12452）。
> **宁可慢一点，用已经验证过的包围盒。**

### 顺带修掉的一个边界情况

半整十俯角（如 −40°）时，**地平线正好落在画面顶边**，`z = d·f` 会算成 **0**，
于是 `x/z` 得到一个"看似正常"的 `0` —— 把地平线误判成"在画面里"。
已在 `ground_point_in_frame` 里加 `z <= 1e-9` 防护。

## 五、修法 B（根治）：**结论 —— 暂时不做**（2026-10-13 用数据定的）

### 先把影响面量清楚

**① 四边形 vs 真实足迹的面积差**（鞋带公式，按周长顺序采样）

```
收口帧  : 平均 +20.15%，最大 +24.51%
非收口帧: 平均  +0.0000%，最大 -0.0000%   ← 完全精确
```

> 注意方向：四角四边形是真实足迹的**内接**形状 ——
> 收口把远边两个角沿各自方向缩到同一距离，两点间的直边**切在圆弧内侧**，
> 所以四边形**偏小**（漏覆盖），不是偏大。
> 我一开始说反了（"多算"），是点序没排好导致鞋带公式算出自交多边形，
> 修正后才看清。

**② 收口帧占多少**

| 架次 | 可用帧 | 收口帧 | 占比 | 俯角中位 |
|---|---:|---:|---:|---:|
| DJI_...095258 | 12116 | 4122 | **34.0%** | −30.8° |
| DJI_...101516 | 12453 | 4281 | **34.4%** | −30.1° |

收口阈值是 `CLIP_PER_ALT = 12 × 高度`（97 m 高度 → 1164 m）。
俯角中位 −30° 时远角刚好越过这条线，所以**三分之一的帧**都会收口。

**③ 对格子的实际影响**（同判据抽样，跨俯角）

```
合计：多算 3.75%，漏算 8.54%（抽样 180000 点）
非收口帧：多算 0.0%、漏算 0.0%
```

### 那为什么还是不做

| 维度 | 判断 |
|---|---|
| **用户遇到的问题（检索到不包含该点的帧）** | **A 已经完全解决**（实测 26% → 0） |
| **B 能额外修好的** | 收口帧的覆盖边界**偏内约 20% 的足迹面积**；一个架次约 6.8% 的整体覆盖（34% 帧 × 20%），换算到 494 公顷约 **34 公顷** |
| **代价** | `frame_footprint` 从 4 角变 4+N 点 → 栅格化要改成凸多边形、矢量化要跟着改、**全部网格重建（1~3 分钟/架次）**、置信度分母要重标定 |
| **风险** | 中高：动的是**整条几何链**，而 A 已经把用户能感知的问题挡在查询层了 |
| **改动收益比** | 低 —— 用户近期用不到"边界精确到 ±20 m"这个精度 |

**决定：不做 B。** 但把它作为**已知限制**写清楚（就是本节），
并保留 A 在查询层的精确射影判定 —— 那才是"给用户看的结果必须对"的那一层。

### 什么时候该回头做 B

出现下面任一条，B 就该提上日程：

1. 需要**按覆盖范围算面积/出图**（例如"这条堤岸有多少公里被覆盖到了"），
   ±20% 的边界误差会直接影响结论
2. 有人反馈"热力图边界比实际少了一块"，尤其在浅俯角扫视段
3. 要把覆盖栅格**归档/交付**给别人用

### 另外一条更省的路（也没做，记着）

真正的病灶是 `CLIP_PER_ALT = 12 × 高度` **定得太紧** —— 俯角中位 −30° 就撞线，
所以 34% 的帧都收口。**把上限放宽到 20× 高度，大部分帧就不再收口**，
四边形也就自然精确了（非收口帧误差是 0.0000%）。

但代价是：那些远边区域的 GSD 最差、对姿态误差也最敏感
（实测 −23° 时 0.25° 的俯角误差会带来 ±2.3 m 的位置误差），
所以别顺手改 —— 改了要重跑置信度标定，并把上限本身当成一个**待实测**的参数。
