# 视场覆盖栅格 · 原型验证结果与落地方案

> 路线（用户 2026-10-12 定）：**先栅格，后矢量**。用「每个栅格被多少帧覆盖」做统计，
> 覆盖次数越多可信度越高；只扫过一两秒的是低可信度。
>
> 本文件是一次**真跑原型**的结果：跑了 2 段真实素材，验证了几何、量级、性能，
> 并发现两个 bug 和一个必须修正的设计问题。

---

## 〇、结论

**路线成立，热力图效果已经出来了**（见文末图）。但实测暴露一个关键问题：

> **"覆盖帧数"不能单独当可信度** —— 它主要反映无人机在哪儿悬停/驻留，
> 而不是那儿看得清不清。实测那段 20 分钟视频里，覆盖格的中位数是 **231 帧**、
> 最高 **1580 帧**，但那只是"镜头一直对着那儿"。
>
> **必须再叠一个与距离有关的质量指标**（地面分辨率 GSD）。这个指标一加上，
> 图上的"高价值区域"立刻收敛到很小一块（见对比图右侧）。

## 一、跑出来的结果（真实素材）

| | 司空 2 样本（36 s / 361 帧） | 大素材（20 分钟 / 12116 帧） |
|---|---|---|
| 网格 | 1320×1320 @ 2 m | 1377×1377 @ 2 m |
| 处理耗时 | 0.1 s（2408 帧/秒） | **29.1 s（417 帧/秒）** |
| 单帧四边形面积 | p50 1.39 公顷 | **p50 42.95 公顷**（p95 77.5） |
| 覆盖面积 | 67.5 公顷 | **494.5 公顷** |
| 变焦镜头覆盖 | 无（全程广角） | 仅 2.06 公顷（**0.4%**） |

### 「覆盖帧数」的分布（大素材）

```
p25 75   p50 231   p95 1001   max 1358

≥  30 帧： 85.8%   424.4 公顷
≥ 100 帧： 70.7%   349.4 公顷
≥ 300 帧： 37.1%   183.5 公顷
```

**读法**：中位数 231 帧看起来"很可信"，但这是 **20 分钟里同一片地反复被拍到**的结果，
不代表看得清。所以单看这个数会误导。

### 「最优地面分辨率 GSD」的分布（同一份数据）

```
GSD ≤ 0.05 m/px（能看清  5 cm）：  1.4%     7.0 公顷
GSD ≤ 0.10 m/px（能看清 10 cm）：  5.3%    26.2 公顷
GSD ≤ 0.20 m/px（能看清 20 cm）： 21.1%   104.1 公顷
GSD ≤ 0.50 m/px（能看清 50 cm）： 93.6%   463.1 公顷
中位最优 GSD：0.32 m/px
```

**这才是"能不能看出东西"的度量** —— 而且它和帧数几乎不相关。

## 二、对比图说明了什么

![覆盖对比](_cov3_DJI_20260924095258_0001_V.png)

- **左：覆盖帧数** —— 暖色集中在无人机驻留/盘旋的一带，向外渐冷。
  这张图很好看，也确实反映"飞过哪里、停了多久"。
- **右：最优解像度** —— 大部分区域是蓝色（**看不太清**），
  只有极小一块红/橙（**真正看得清的地方**），另有零星的绿色小方块（变焦镜头拍过的点）。

**两张图像不一样，说明它们回答的是两个不同问题：**

| 问题 | 该看哪个 |
|---|---|
| "这片区域被拍到了吗？" | 左（覆盖帧数） |
| "这片区域**能不能看清**？" | 右（GSD） |
| "这块是不是反复观测过、可信？" | **两个都要** |

**建议的最终可信度 = 覆盖帧数（够多） × 最优 GSD（够清）**，
两者都达标才算"高可信度"，只有其一的降级标注。

## 三、原型里发现并修掉的两个 bug

### bug ① 收口误伤了近边（**这个 bug 会让结果完全失真**）

收口逻辑本意是"远端打不到地面时，把它截在 12×高度 处"。
但原实现对**四个角点**都做了收口，包括画面**下边缘**（最近的那条边）。

在浅俯角 + 高空时，下边缘的地面距离本来就可能超过收口上限，
于是**近边被错误地推到远处**，整个四边形被压扁成一条窄带。

**实测影响**：12116 帧里有 **1980 帧（16.3%）** 的近边距离超过收口上限 → 全部失真。
修掉之后，同一份数据的处理耗时从 **122 s 降到 29 s**（因为不再盖那么多冤枉格子），
说明原来那版算出的覆盖图是错的。

**正确做法**：只对 `yImg = +1`（画面**上**边缘 = 地面**远**端）收口；近边永不收口。

### bug ② 渲染时南北画反了

我的可视化脚本把屏幕 y 增大当成了"向北"，实际应该是向下。
判据：无人机 `yaw ≈ 0°`（朝北）时，覆盖形态应该**向图上方（北）展开**。
修正后图上三角形朝上 —— 与数据一致。

> 这两个都是**原型脚本**里的问题，不是页面里几何代码的问题（页面的 `footprintGeometry`
> 本来就只在左右两条边上取点、且只在指定距离处收口）。列出它们是为了说明：
> **这种几何一定要先可视化看一眼，光看数字看不出错。**

## 四、性能与优化方向

| 版本 | 大素材（12116 帧） | 说明 |
|---|---|---|
| 修正版·只数帧数 | **29 s** | 可用 |
| 修正版·带 GSD 质量 | **416 s（约 7 分钟）** | **太慢**，因为每格都要算 sqrt 与除法 |

**瓶颈**：纯 Python 逐格循环。优化顺序：

1. **换 numpy 数组**（现在用的是嵌套 list）—— 预计 **10~30 倍**
2. **GSD 按"帧 × 距离带"预计算**：同一帧在网格上的距离是渐变的，
   不必逐格算 `hypot`，可按行近似
3. **只对"低分辨率"格跳过质量计算**：远到一定距离（GSD > 阈值）直接不记质量
4. 后台任务 + 进度（20 分钟视频必须异步跑）

**目标**：大素材 **≤ 30 s**（与只数帧数同量级）。

## 五、落地方案

### 数据结构（每个视频一套）

| 数组 | 类型 | 内容 |
|---|---|---|
| `count` | uint16/uint32 | 覆盖帧数（**用户要的热力图**） |
| `gsd_best` | float32 | 该格**最好一次**的地面分辨率（米/像素） |
| `zoom_hit` | uint8 | 是否被变焦镜头（>40 mm）拍到过 |

> 两个镜头档**各一套**还是共用一套？建议**共用一套 + 记录该格的最佳 GSD**，
> 因为"变焦覆盖"本质上已经由 GSD 表达（变焦的 GSD 天然更小）。
> 额外用 `zoom_hit` 标一下"这里做过变焦详查"，用于展示。

内存估算（2 m 网格、2.5 km 见方）：1377² ≈ 190 万格
→ `count` uint32 = 7.6 MB、`gsd` float32 = 7.6 MB、`zoom` uint8 = 1.9 MB ≈ **17 MB/视频**，可接受。

### 接口

| 接口 | 作用 |
|---|---|
| `POST /api/project/coverage/build` | 为某视频构建（后台任务 + 进度） |
| `GET /api/project/coverage/query?lat=&lng=` | **回答"这个点被拍到没有"**：返回覆盖帧数、最优 GSD、能否看清 N cm、是否变焦详查过、哪段时间 |
| `GET /api/project/coverage/heatmap?...` | 热力图 PNG（**左：帧数 / 右：解像度**，或按参数选） |
| `GET /api/project/coverage/polygon?metric=count\|gsd&threshold=N` | **栅格 → 矢量**（GeoJSON），阈值可调 |

## 六、给面试/汇报时的一句话

> "把每一帧的相机视场投影到地面、在 1~2 m 的网格上累计覆盖帧数，
> 就得到一张『哪里被反复观测过』的热力图；
> 再叠一层地面分辨率，就能回答『这个经纬度**不仅被拍到、而且看得清**』。
