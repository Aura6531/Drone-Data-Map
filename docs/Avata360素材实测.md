## 一、读得出来，格式清楚了

- `ffmpeg / ffprobe` **能直接读 `.OSV` 和 `.LRF`**（都是 MP4 家族容器）。
- `ffprobe` 报 **2 条 3840×3840 视频流 + 1 条 960×540 数据流**。
  抽第一路出来看是**单个圆形鱼眼**；而 `.LRF`（单路 1920×960）是**两个圆并排**。
  → **双镜头原始输入是"两个鱼眼圆"**，`.OSV` 里应当是每路一路、或已拼好。
  > 这一点还没完全定论（见"待确认"），但不影响下面的判断。
- 全景照片是**标准等距柱状**（2:1 = 15520×7760），单帧 1.2 亿像素。

## 二、真正的阻塞点：SRT 里没有定位，也没有姿态

```
[iso: 2500] [shutter: 1/100.0] [fnum: 1.9] [ev: 0] [ct: 4171]
[color_md: default] [ae_meter_md: 0]
[latitude: 0.000000] [longitude: 0.000000] [rel_alt: 0.900 abs_alt: 2715.459]
```

- **`latitude` / `longitude` 整份文件全是 0.000000**（1580 个采样点，非零 0 个）
- **完全没有 `gimbal_pitch` / `gimbal_yaw`**（M4T 的 SRT 有，这份没有）
- `rel_alt` 只在 **0.3 ~ 0.9 m**，`GPSStatus = V`（无效），`GPSLatitude = (0,0,0)`

照片的 EXIF 也一样：`GPSLatitude (0,0,0)`、`GPSStatus V`（invalid）、只有绝对高 2715.668 m。

**结论：这是一次室内测试录制**（抽帧画面就是你房间的天花板/地板），
**没有卫星定位、没有云台姿态、飞机也没怎么动。**

## 三、这对"融进数据地图"意味着什么

| 要做的事 | 现在能不能做 |
|---|---|
| 把 360 视频**当视频播放** | **能** —— 只要解出等距柱状或双鱼眼，就能用现有播放器 |
| 把 360 视频**叠到地图上** | **不能** —— 没有经纬度，无从定位 |
| 算 360 的**视场覆盖** | 几何可以推（见下），但**算出来的东西没地方放**（缺定位） |
| 用 360 做**跨架次检索** | **不能** —— 检索的前提是"哪个位置被拍到"，这需要定位 |

### 附：360 的视场几何其实比针孔**更简单**，值得先记下

等距柱状里，仰角只由**像素行**决定：

```
θ(仰角) = f(row)，与偏航无关
地面距离 d = h / tan(仰角)
```

也就是说——**一帧 360 覆盖的是一个"圆环"**，不是梯形。
镜头若有俯仰，正下方会出现一个**盲区**（内半径 = h·tan(俯角)）。

所以现有的 `frame_footprint()`（针孔四角）**完全不适用**，需要另写一族函数。
但推导本身是初等的，不难。

## 四、待确认 / 下一步

1. **`OSV` 到底是"双鱼眼"还是"已拼等距柱状"？**
   上面两种证据（`ffprobe` 报两条 3840×3840 流、LRF 是双圆）需要再确认一次：
   分别把两路流各抽一帧对比，就能定论。
2. **有没有带 GPS 的飞行素材？**
   这次是室内测试。如果 360 视频是在**室外飞行**时录的，SRT 里应当有经纬度
   （`rel_alt` 0.3~0.9 m 说明这次飞机几乎没起来）。
   想接着往下做的话，**最有用的是再录一段有定位的**。
3. **要不要先做一个 360 预览器？**
   双击 `.OSV` 就能拖动看方向（等距柱状 → 透视小窗，或者双鱼眼 → 等距柱状）。
   不依赖定位、不依赖地图，独立可用，也能顺便把投影换算验证清楚。
