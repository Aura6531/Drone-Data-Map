## 一、为什么必须转码

`.OSV` 的实际内容（ffprobe 实测）：

```
流 0   hevc Main10   3840×3840 @59.94fps   105 Mbps   ← 鱼眼：天空
流 1   hevc Main10   3840×3840 @59.94fps    96 Mbps   ← 鱼眼：地面
流 2/3 djmd（元数据）   流 4 camd   流 5 mjpeg 960×540（低清预览）
```

两层问题：

1. **浏览器解不了 HEVC Main10** —— 实测报 `does not support the video's codec`。
2. **就算能解也没用** —— `.OSV` 存的是**两颗独立的鱼眼圆图**（背靠背），
   不是成熟的全景。重投影必须有人做。

所以：**转一次成等距柱状 H.264，之后浏览器 `<video>` 直接播。**

## 二、跑通后的链路

```
点检索结果里的 360 命中
   ↓  window.open('/pano360_player.html?name=&rel=&t=&yaw=&pitch=&fov=')
播放器页面 boot()
   ↓  GET /api/pano360/transcode?name=&rel=&tier=
          · 已转过（pano_cache/<stem>_<tier>.mp4 存在）→ 立刻返回 cached:true
          · 没转过 → 现场转（分钟级），返回 seconds / resolution
   ↓  转好后再向 /pano?name=&rel=&tier= 取视频
   ↓  /pano 用 HTTP Range 流式送出（<video> 拖进度必须）
   ↓  等距柱状帧 → canvas 逐像素做透视取景 → 拖拽/滚轮/方向键改视角
```

### 接口

| 接口 | 说明 |
|---|---|
| `GET /api/pano360/transcode?name=&rel=&tier=&force=` | **异步**提交转码；已转过返回 `cached:true`，否则返回 `job` id |
| `GET /api/pano360/job?id=` | 查任务进度（省略 id 返回全部 + `active` 数） |
| `GET /api/pano360/precache?name=&tier=&force=` | **批量预转**该项目所有 `.OSV`，返回排队列表 |
| `GET /pano?name=&rel=&tier=` | 流式送出转码产物，**支持 Range**（206） |
| `GET /pano360_player.html` | 播放器页面（播放 + 拖拽转向） |
| `GET /pano360.html` | 老的逐帧预览器，**保留**作为"不想等转码"的退路 |

预览页里的跳转：**默认开播放器**；加 `&mode=frame` 就退回逐帧预览器。

#### 为什么转码接口是异步的

转码是**分钟级**（79 秒素材约 7 分钟）。同步接口有两个问题：
前端只能干等、看不到任何进度；请求挂那么久容易被浏览器或代理掐掉。

改成"提交任务 → 轮询进度"后，前端能显示百分比、已处理秒数、速度、已等时长：

```
进度   0.0% → 12.0% → 20.2% → 28.4% → … → 97.1%
速度 0.291x → 0.351x   fps 18.17 → 21.26
```

**并发度 = 1（串行）**：转码本身会把 CPU 吃满（4K HEVC 软件解码 + 重投影），
并行跑多个只会互相拖慢，而 GPU 只有一块。串行反而总吞吐更高、也更可预期。

### 产物位置

```
Data/<素材目录>/pano_cache/<素材名>_<tier>.mp4
```

放在素材旁边（同目录的 `pano_cache/`），便于随素材一起搬走/清理。

### 产物有效性判据：不能只看 `size > 0`

踩过：转码中途被杀会留下 **0.0 MB 的残片**（实测见过
`DJI_20261014110343_0002_D_quick.mp4`）。`size > 0` 会把它当成"已转好"，
于是**缓存永远命中、永远放不出画面**，而用户不知道该删哪个文件。

改用 `is_valid_output()`：**`size >= 1 MB`**。
最快档 10 秒的片段也有十几 MB，所以这个阈值能挡掉所有残片，又不会误伤真产物。

### 踩过的一个死锁

`/api/pano360/job` 一上线就**永久挂住**（而 `/api/config` 等接口正常，很难猜）：

```python
def all_jobs():
    with _jobs_lock:          # 普通 threading.Lock —— **不可重入**
        return [job(i) for i in _jobs]   # job() 里又去拿同一把锁 -> 死锁
```

改成"先取 id 列表、出了锁再逐个构造快照"。修好后
`all_jobs` / `active_jobs` / `job` 三个都能在 8 秒内返回。

## 四、显卡：优先 NV，已确认走独显

用户 2026-10-16：「显卡是有两个的，一个是AMD的核显，另一个是NV的4060，优先用NV的」

代码里的优先顺序（`HWACCEL_CANDIDATES`）本来就是 cuda 在前：

```python
HWACCEL_CANDIDATES = ("cuda", "d3d11va", "d3d12va")
```

实测探测结果 `probe_hwaccel = cuda`、`h264_nvenc = True`。

**转码时用 `nvidia-smi` 实时采样，确认真的在 NV 上跑**：

```
GPU: 18% / 14% / 20%     解码器: 14% / 15% / 13%     NVENC: 0% / 11% / 0%
显存占用 2988 MiB
```

解码器（NVDEC）与 NVENC 都在动 → **走的是 4060，不是核显**。

注意 GPU 占用只有 10~20% —— **瓶颈在 CPU 侧的重投影**，GPU 还有大量余量。

## 六、没做成的：GPU 重投影

想把它搬上 GPU（因为它是大头，不是解码/编码），**没成功**：

| 尝试 | 结果 |
|---|---|
| `remap_opencl` | 崩在 libx264 编码阶段（`vost#0:0/libx264 ... return code -22`），像素格式没协商好 |
| `v360_vulkan` | **单输入滤镜**，它的 `dfisheye` 期待的是一张排列好的双鱼眼图；而 `.OSV` 的两路是**同一文件的两个独立流**。所以它只吃到一路，**几何不可能对** —— 测出来的"快 2.1 倍"是**假快** |

`v360_vulkan` 那条特别值得记：**它跑得通、也快，但结果是错的。**
如果我只看速度不看几何，就会把一个错的方案当成优化成果。

## 八、导入时自动预转（已完成）

用户说「不怕预加载和导入的过程中生成文件」—— 所以**导入数据时顺手把 360 素材排进队列**，
之后点开任何 360 素材都是秒开（否则第一次点要等几分钟）。

```
POST /api/project/add-folder
  → 保存文件夹
  → queue_pano_precache(project, scan_root=<刚加进来的文件夹>)
  → 返回 { success, project, pano_precache: {queued, already_done, error} }
```

设计要点：

- `queue_pano_precache()` 抽成公共函数，**手动接口 `/api/pano360/precache` 与导入共用**
  （两处写两遍迟早不一致）。
- `scan_root` 只扫**刚加进来的那个文件夹**，不重扫整个项目。
- **预转失败不能影响导入本身**：主结果是"文件夹导入成功"，
  所以异常被捕获进 `pano_precache.error`，接口照常返回 success。
- 已转好的（`is_valid_output`，≥1 MB）会跳过，不重复排队。
- 前端要显示的提示是
  `N 360 clip(s) transcoding in the background — they will open instantly once done.`

**实测验证**（临时项目 + 假 `.OSV`，走真实的 `queue_pano_precache`）：

```
临时项目里有 3 个 .OSV（其中 1 个已"转好"，2 MB）
① 排队 2 个，已转好跳过 1 个                    [OK]
② 任务表里 2 个任务：running + queued            [OK]
```

这条同时验证了 `is_valid_output` 的 1 MB 阈值 —— 2 MB 的产物被正确认成"已转好"。
