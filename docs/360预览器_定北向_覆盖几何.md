## 二、② 定北向：解出来了（用太阳）

**原理**：太阳的**地理方位角**由「时间 + 位置」独立算出（精度约 0.02°），
而它在全景图上的**相机系方位角**可以量出来。两者之差就是北向：

```
north_yaw = az_theory − phi_measured
        = 139.26 − (−81.53) = −139.21°
```

**关键性质：这个结果与 FOV 标定无关。** 因为只用方位角，
而像面方位角 `phi = atan2(dy, dx)` 是把像素绕圆心取角度得到的、不涉及极角映射。
所以即使 FOV 还没定准，北向也是可信的。

### 两段素材的实测结果

| 素材 | north_yaw | 日面量测 | 可信 |
|---|---:|---|---|
| `..._110343_0002_D` | **−139.21°** | r/R 0.4534（预期 0.4716，差 −0.018）日面 2664 px | ✓ |
| `..._105342_0001_D` | **−28.78°** | r/R 0.4678（预期 0.4865，差 −0.019）日面 2822 px | ✓ |

> 两段的 north 相差 110°，说明**两段飞行之间相机/机身朝向变了** ——
> 这在素材上是合理的（同一架飞机的下次起飞，摆放朝向不同）。
> 但它们各自的**相机系**太阳方位只差 31°（220° vs 251°），与飞行朝向变化的量级一致。

### 可信度检查（两道，都是踩坑后加的）

1. **日面必须落在"由太阳高度角预测的半径"附近**（容差 0.06）。
   水面反光/建筑反光不会落在这儿 —— 实测某时刻把 r/R=0.85 的**河面反光**
   当成太阳，算出的 north 差了 170°。
2. **过曝块必须像个盘**（>= 800 px）。实测有过 **305 px 的碎片**被当成日面，
   给出 +71° 的错方向；真日面在这个尺度上是 1700~3000 px。

**不过检查就返回 unknown，绝不猜。错的方向比没有方向更危险。**

### 关键设计决定

1. **不动针孔那条**。`build_from_telemetry` 里判 `pit is None or yaw is None` →
   走 360 圆环分支；有 `yaw/pitch` 时仍走原来的四边形路径。
   测试里专门钉住了"针孔正下视的足迹四角**等距**（正方形）"、
   "边长 = 2·h·tan(fov/2)"，防止被 360 那套带坏。
2. **圆环不用多边形近似**。`_raster_frame` 是"按行与四边形交点对"填充的（even-odd），
   圆环带洞、填不对。所以单写 `_raster_sphere_ring`，逐行算
   `near² <= d² <= far²` 的列区间 —— 比多边形近似**更准也更快**（3 s 建完）。
3. **远半径复用针孔的收口参数**（`CLIP_PER_ALT × h`，下限 `CLIP_MIN`）。
   针孔那边已经解决了"仰角趋近 0 时 d→∞"这个一模一样的问题，它的默认值是实测调过的；
   360 再发明一套只会多一个没人验证过的旋钮。副作用是两边网格尺度一致、可比。
4. **内半径默认取 0**（假设整球覆盖）。因为 360 的 SRT 里**没有**云台姿态，
   正下方的盲区**无法从数据得知**。取 0 是保守且对全景基本正确的假设；
   **这是已知的近似**，写在 `sphere_ring()` 的文档里。
5. **存下逐帧单像素角**（`CoverageGrid.frame_ang_per_px`）。
   360 没有焦距（`frame_focal` 保持 0，不编一个假值），
   查询时靠这个字段反推斜距 —— 否则 `rad_per_px(0)` 会除零（真踩过）。
6. **`sigma` 在缺俯角时不能变成 inf**。`sigma_footprint(pitch=0)` 返回 inf，
   会把置信度压成 0。360 的边界不确定度只由地表高差决定，所以直接取 `dh_terrain`。

### 径向标度：两段素材独立印证到 0.02%

覆盖几何唯一需要的标度是"每单位归一化半径对应多少度极角"。它**可以用太阳实测反推**：

| 素材 | 太阳高度角 | 极角 | 日面 r/R | 径向标度 |
|---|---:|---:|---:|---:|
| `110343_0002` | 42.84° | 47.16° | 0.4534 | **104.01** 度/单位 |
| `105342_0001` | 41.35° | 48.65° | 0.4678 | **104.00** 度/单位 |

**相对差 0.02%** —— 两个不同时刻、不同太阳高度角、不同相机朝向的独立测量。
所以取 `DEG_PER_UNIT_R = 104.0`（即 FOV = 208°）。
这比"猜 FOV"可靠得多，也是 ③ 能用起来的前提。

### 为什么要给 360 单开一条缩略图链路

整张全景是 2:1 展开图，**直接当缩略图没法看**（一片弯的）。
所以缩略图是"从全景按**目标点方向**裁出来的一张透视小图" ——
这既是有判读价值的画面，也顺手把"镜头该转向哪"这件事解决了。
实测每张 **0.05~0.07 s**（全景本身有缓存，只做裁剪）。

### 为什么 360 命中不能直接播

`.OSV` 是 **HEVC Main10（10bit）**，浏览器普遍解不了 —— 实测报
`does not support the video's codec`，画面全黑。而且 14.5 GB / 10 分钟，
走原来那套"按需转码片段"也不现实。所以 360 命中改成**打开 360 预览器**：
预览器是服务端逐帧渲染的，不依赖浏览器解码。

### 全景质量：两个拼接坑（都踩过、都修了）

改完前端后看预览器截图，发现全景里有**一道横贯的白色圆弧**和**一条黑带**。
两个根因：

| 坑 | 症状 | 根因 | 修法 |
|---|---|---|---|
| **白环漏进全景** | 纬度 −11° 附近一道白弧 | 鱼眼外圈那道**人造白环**被采样到了（`r/R≈0.97` → θ≈101°） | 采样点落在环上就**跳过** |
| **黑带** | 纬度 −10° 附近一条黑带（60 px） | 一开始是"把环**涂黑**"→ 等价于让上镜头拿**黑像素**去占位，**盖掉了下镜头本该填的有效内容** | 改成"跳过"（不占位），让另一路填 |
| **白弧仍在** | 黑带没了但白弧还在，且**不对称** | 上镜头的白环**是不对称的**（0° 方位在 r/R 0.99~1.00、270° 方位在 0.95~0.96）。"上镜头优先"会让它用**边缘最差区域**去覆盖本该由下镜头**中心区**负责的地带 | 改成**按极角择优**：每个像素选 `θ` 更小的那一路（=离光轴更近、畸变更小） |

修完的实测：


- **图像圆的真实边缘在 `r/R = 0.998`**（不是 0.93）—— 两颗镜头都是。

- **白环不是一个干净的圆**，径向位置随方位变（0.95~1.00）。

## 五、FOV 定准了（用太阳，两段独立印证）

我一开始用"两路接缝一致性"去标定，**失败了**：

- 造一张**已知标定**的合成图（正向模型生成），在**正确** FOV 上失配是 **6.62**（不是 0）
- 而真实素材的失配在 50 上下

**判据的分辨率不足以定 FOV**（理想数据上就有 ~7 的偏差）。
好在**根本不需要它**：覆盖几何要的是"每单位半径多少度"，而那个可以用太阳实测给出，
两段独立测量一致到 **0.02%**（见 ③ 那一节）。北向更是完全不依赖它。

> 也顺带证明了另一件事：我一开始设计的 sanity check（"同一张图当两路，失配应为 0"）
> **本身是错的** —— `t` 与 `π−t` 的方位角关系不是恒等，同一张图的两路采样点**本来就不重合**。
> 这个错误的 sanity 让我误判了好几轮。换成"合成图 + 已知标定"才是对的判据。

## 六、开发中踩的坑（都写进代码注释了）

| 坑 | 症状 | 正确做法 |
|---|---|---|
| **像面手性** | 下镜头的 `phi` 写成 `-atan2(dx,-dy)`（把"光轴反向"误当"像面镜像"）→ **天空像素被下镜头抢走，太阳填到地平线以下**（实测高度角 −4.8°，真值 +42.8°） | 两个镜头用**同一个** `phi = atan2(dx, dy)`；区别只在世界分量 `(dx, ±dy, ±cz)` |
| **鱼眼外圈白环** | 它比日面更亮更大 → "取最亮区"抓出 r/R=0.971 的假太阳 | 先遮掉 `r/R > 0.93` |
| **水面反光** | 比日面更亮 → north 差 170° | 只用"预测半径 ±0.06"环带里找 |
| **反光斑的边缘** | `r_tol=0.18` 太宽，60px 反光斑的**边缘**落进环带，与日面连通成一块 | 容差收到 0.08（服务里 0.06） |
| **亮度互相关定 FOV** | 两个径向亮度剖面都是"山-天-地"的相似结构 → 任何对齐都相关，给出 FOV=286°（物理不可能） | 换有物理硬约束的判据（太阳高度角） |
| **"同图自比"的 sanity** | 以为同一张图当两路失配应为 0；实际两路采样点本就不重合，该判据恒不成立 | 用**合成图 + 已知标定**验证 |
| **等距柱状图上找太阳** | 无特征场景里"最亮区"是沙滩反光（1 万像素）→ 算出 +10.7° | 在**鱼眼原图**上量，并肉眼核对标注图 |
| **`rad_per_px(0)` 除零** | 360 没有焦距，`frame_focal = 0` → 点查询崩 | 存下逐帧单像素角 `frame_ang_per_px` |
| **`sigma_footprint(pitch=0)` 返回 inf** | 360 缺俯角 → 置信度被压成 0 | 缺俯角时取 `dh_terrain` |
| **圆环不能用 even-odd 填** | 网格化按"行与四边形交点对"填充，圆环带洞填不对 | 单写 `_raster_sphere_ring`，直接判 `near²<=d²<=far²` |
| **检索不去重** | 采样 20 Hz，某点命中 1248 帧 → 同一瞬间列 1248 次 | 按 `FIND_DEDUP_SECONDS` 合并 + `FIND_PASS_GAP_SECONDS` 切趟 |
| **把鱼眼白环"涂黑"** | 全景里一条横贯黑带（60 px）—— 涂黑等于拿黑像素占位，盖掉了另一路的有效内容 | 环上的采样点**跳过**（不占位） |
| **"上镜头优先"填全景** | 地平线附近一道**白弧**（白环不对称，上镜头拿边缘最差区域覆盖了下镜头的中心区） | **按极角择优**：选 `θ` 更小的那一路 |
| **把遮罩半径猜成 0.93** | 人为造出 13° 假缺口（真实边缘在 `r/R=0.998`，两路重叠 27.6°） | 先量再设：`ring_inner=0.99` |
| **`rad_per_px(0)` 除零** | 360 没有焦距 → 点查询崩 | 存下逐帧单像素角 `frame_ang_per_px` |
| **列表接口现算北向** | `/api/pano360/list` 每段抽帧几秒 → UI 进页面就卡 | 列表**只读缓存**；现算推迟到真正出卡片时 |
| **在锁内调拿同一把锁的函数** | `render_perspective` 拿 `_render_lock` 又调 `render_cached`（也要拿）→ **死锁**（进程挂住、缓存毫无动静） | 不拿锁（拼接那步由 `render_cached` 保护） |
| **pitch 符号搞反** | 预览器 `pitch=-45°` 看到的是**天空** | 旋转矩阵要与 `stitch` 的逆式一致；用**人造经纬度全景**做可自证的回环测试 |
| **实心 vs 空心的 sanity** | "同一张图当两路，失配应为 0"这个 sanity **本身是错的**（`t` 与 `π−t` 的方位角关系不是恒等） | 换成"合成图 + 已知标定" |

## 七、留了东西给用户

- **地图上直接用**：选点 → `Frames of this spot` → 图墙里针孔和 360 的结果**混在一起**，
  360 的卡片标着 `360` 和 "sphere (no gimbal)"，缩略图是按目标点方向裁的透视小图
- **点 360 卡片**会开一个新标签页的**全景预览器**，镜头**已经对准**你选的那个点
- 预览器支持 `?rel=&t=&yaw=&pitch=&fov=` 深链（图墙就是这么跳的）
- 北向是**自动算 + 缓存**的（`<视频目录>/.pano_cache/north_*.json`），
  换了素材重新算，不需要手工填表
- 缓存目录也存渲染好的全景帧和透视小图（上限 400 张，LRU 清理）

## 九、还没做的（都不影响上面三条）

- **正下方盲区**：360 的 SRT 里没有云台姿态，正下方盲区**无法从数据得知**，
  现在按"整球覆盖"处理（内半径 0）。这是**已知近似**，写在 `sphere_ring()` 文档里。
- **单像素角是代理值**：用 24 mm 等效（≈0.000347 rad）。它让 GSD 有一个**乘性比例误差**，
  但不影响覆盖范围（覆盖只由高度与仰角决定）。
- **`angles` 档对 360 无意义**：全景是整球，没有"换角度"这回事。
  前端如果传 `mode=angles`，后端会落到 `passes`。
- **1.05 GB 的 `.LRF` 没用上**：那是 1920×960 的双鱼眼预览流，比 3840×3840 的 `.OSV` 小得多，
  如果只做检索缩略图其实可以拿它当快速通道（现在没走）。
