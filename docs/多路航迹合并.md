# 一次拍摄的多路航迹合并为一份

> 用户 2026-10-15 的要求：
> 「3个航迹几乎一样，地图只画一个线没问题，内部文件 geojson 保留 1 份即可，
> 增加两个数据列嘛，对应：T 的帧数、V 的帧数、S 的帧数，
> 这样统一调用、查阅；SRT 你看着判断，如果能只做一个是最好的。」
>
> 以及随后确认的：「『把三路视频的帧号作为逐点数组存进去』——就这么干」

---

## 一、为什么"三份"是问题

一次拍摄（一次起飞）产出**三路视频**，各自带一份 SRT：

| 路 | 内容 | 分辨率 | 帧率 | 帧数 | 视频体积 |
|---|---|---|---:|---:|---:|
| `_V` | 可见光混合变焦（4K 主码流） | 3840×2160 | 29.78 | 36542 | 6254 MB |
| `_S` | 同一视角的 1080p 版本 | 1920×1080 | 29.75 | 36550 | 2039 MB |
| `_T` | 热成像（机内 2× 放大后录制） | 1280×1024 | 30.00 | 36858 | 1189 MB |

以前每路各生成一份 geojson，于是**地图上画三条几乎重合的线**、文件列表里同一次拍摄出现三次。

### 定位数据确实几乎一样

按**时刻对齐**逐点比较（不是按下标 —— 按下标比会得出"差 159 m"这种**错位伪影**）：

```
组 1: V vs S  中位 0.000 m   p95 1.25 m  最大 1.64 m
      V vs T  中位 0.000 m   p95 1.48 m  最大 1.96 m
组 2: V vs S  中位 0.410 m   p95 1.54 m  最大 1.75 m
      V vs T  中位 1.488 m   p95 4.50 m  最大 5.97 m
```

0~6 m，正是 GNSS 抖动级别（项目自己的 `D_GNSS = 1.5 m` 就是这个量级）。

### 但**帧号推不出来**

这是关键，也是为什么必须逐点存数组而不是存"三列帧数"：

| 证据 | 数据 |
|---|---|
| 帧率不同 → 会累积漂移 | 同一时刻 `S−V`：前 1/4 中位 **−29** → 后 1/4 中位 **+2**（漂移 31 帧） |
| 同上，热成像更明显 | 同一时刻 `T−V`：前 1/4 中位 **+50** → 后 1/4 中位 **+231**（漂移 **181 帧**） |
| `FrameCnt` 与 `cue×fps` 的残差不是常数 | V 的残差偏离中位达 **41 帧** |
| 三路各有丢帧（`FrameCnt` 不连续） | V **49** 处、S 10 处、T 11 处 |

实测同一时刻三路的帧号（合并文件里的真实数值）：

```
t=    0.000 s   帧 {V: 0,     S: 0,     T: 0}
t=  614.280 s   帧 {V: 18297, S: 18282, T: 18433}   ← 差 151 帧 ≈ 画面差 5 秒
```

**所以只存一个数字，跳到另两路视频就会错约 5 秒。**

## 二、做成了什么

### 一份航迹 + 逐点帧号数组

`Data/DJI_202609240950_001/DJI_20260924095258_0001.geojson`（不再带 `_V/_S/_T`）：

```json
{
  "type": "FeatureCollection",
  "name": "DJI_20260924095258_0001",
  "properties": {
    "source_video": "DJI_20260924095258_0001_V.MP4",
    "streams": ["S", "T", "V"],
    "merged_from_streams": true
  },
  "features": [{
    "type": "Feature",
    "geometry": { "type": "LineString", "coordinates": [ ... 36542 点 ... ] },
    "properties": {
      "video": "DJI_20260924095258_0001_V.MP4",
      "videos": { "V": "..._V.MP4", "S": "..._S.MP4", "T": "..._T.MP4" },
      "srt": "DJI_20260924095258_0001_V.srt",
      "reference_stream": "V",
      "streams": ["S", "T", "V"],
      "point_times": [ 0.0, 0.033, ... ],
      "point_frames": {
        "V": [ 0, 1, 2, ... ],
        "S": [ 0, 1, 2, ... ],
        "T": [ 0, 1, 3, ... ]
      }
    }
  }]
}
```

**为什么这比"三列帧数"更强**：给定某个目标点（索引 `i`），
`point_frames[路][i]` 直接就是该路视频里该跳的帧号 —— 不需要推算、不怕漂移。
"三列帧数"做不到这一点（它只能给标量总数，定位不到画面）。

### 体积与加载

| | 以前（三份） | 现在（一份） |
|---|---:|---:|
| 组 1 | 10.41 MB | **2.02 MB** |
| 组 2 | — | **2.05 MB** |
| 全项目 geojson | 8 份 / 17.3 MB | **2 份 / 3.87 MB** |

前端实测（无头 Edge）：

```
① geoFiles=2          ← 一个拍摄一条
② 同一拍摄出现多份的：（没有）
③ 加载 2 条，282 ms   loadedTracks=2   地图 SVG 路径=10
④ geometry.type=LineString  坐标点=36542   streams=["S","T","V"]
   第 5000 点帧号: {"S":5008,"T":5056,"V":5006}
   loadedTracks 里能查到该航迹: true
```

（合并前同样的测量是：加载 6 条 569 ms、`geoFiles=6`、三份重复。）

### SRT 的处置：**保留三份**

因为帧号只存在于各自的 SRT 里。合并进 geojson 之后**处理时**不再需要它们，
但**重新生成**时需要 —— 删了就回不去了。
三份 8.5~12.8 MB，一次拍摄约 30 MB，不占地方。

同时 `SRT_FIELD_RES` 新增 `frame_cnt`（从 SRT 的 `FrameCnt:` 取），
让 `parse_dji_srt_3d` 的记录逐点带上帧号。

## 四、踩的坑（都写进注释了）

| 坑 | 症状 | 原因 |
|---|---|---|
| **`flight_stem_of` 里做了 `.lower()`** | 生成 `dji_...geojson`，而磁盘上是 `DJI_...` —— 在 Windows 上大小写不敏感，于是**多出一个副本**而不是替换旧的 | 生成文件名要保留大小写，比较才小写化 |
| **给 `SRT_FIELD_RES` 加了键、忘了给 `data` 字典加占位** | `load_srt_telemetry` 直接 `KeyError: 'frame_cnt'`，**11 套测试连锁失败** | 解析循环是 `for name, pattern in SRT_FIELD_RES.items(): data[name].append(...)`，少一个键就炸 |
| **`check_project_sync` 按视频名找航迹** | 合并航迹去掉了 `_V`，所以找不到 → **静默退回用 SRT 当参照**，于是查不出航迹本身的问题（测试用例 1 假通过） | 用 `flight_key` 再找一遍 |
| **前端只看文件名推视频路径** | 合并航迹推出 `DJI_x.mp4`（不存在）→ 飞机箭头/图标全建不出来 | 合并航迹必须读自带的路表；见 `VIDEO_REL_BY_GEOJSON` |
| **有两个服务进程在跑** | 改动明明生效了，接口却返回旧结果（一度以为是过滤 bug） | 我之前的"重启"被 `Start-Process` 搞出了重复实例。**重启后要数进程** |
| **测试里按下标逐点比较** | 得出"V vs T 差 159 m"这种结论 | 三路点数不同、时刻错开，按下标比是**错位伪影**；要按时刻对齐 |

## 五、还没做的

- `test_sync.js` 与 `test_nearest.js` 的 mock 还是**合并前的假设**
  （按 `_V` 后缀分三路、按文件名推视频路径），正在更新。
- **界面还没利用新数据**：`point_frames` 已经存进 geojson、前端也读进来了
  （`track.pointFrames`），但检索命中卡片还没显示"这一路该跳第几帧"，
  也没有"切流"的入口。
- **`_S` 是 `_V` 的 1080p 降分辨率版本**（同一可见光视角），视频占 2 GB。
  这是**磁盘冗余**，不是数据冗余 —— 工具不该擅自删素材，但如果要清理，
  `_S` 是最没必要的那个。
