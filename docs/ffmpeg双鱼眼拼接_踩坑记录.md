# ffmpeg remap 拼接双鱼眼：逐个踩坑记录

> 目标：把 DJI `.OSV`（两路 3840×3840 HEVC 鱼眼）转成**浏览器能直接播的等距柱状 H.264**。
> 用户 2026-10-15 定的路线：**走 A 方案（先转码，随点随放）**，
> 并且「可以多跑很多次，时间充裕，先追求最优效果」。
>
> 结论：**管线已跑通**，且与已验证正确的 Python 实现在真素材上等效
> （"差<=30" 占 89.7%、中位差 5.0）。
> 实现见 `Code/pano360_transcode.py`。

---

## 一、为什么不用 Python 逐帧拼接

先量清楚了才决定：

| 做法 | 实测 |
|---|---|
| 随机 seek 抽 1 帧 | **≈ 2100 ms** ← 原来预览器的做法 |
| 顺序解码 | **25~39 fps**（单路）、**17.1 帧对/秒**（单进程两路） |
| Python `stitch()` | 512² 输出 317 ms、1024² 1192 ms、1440² 2330 ms |
| Python 优化后的原型 | 只快 **2.9 倍**（环境里没有 cv2 / scipy / numba） |

**要 30 fps 需要 33 ms/帧，Python 差两个数量级。** 而 `ffmpeg` 的重投影是原生 C。

同时排除了一个误解：**"浏览器播不了 HEVC"不是主因** ——
`.OSV` 存的不是成熟全景，而是**两颗独立的鱼眼圆图**，
就算能解码也得有人做重投影。所以瓶颈在管线，不在浏览器。

## 二、六个坑（每个都是实测确认的）

### 坑 1（最致命）：map 必须 `format=gray16le`

**症状**：输出是"放射状拖尾"的垃圾 —— 像坐标被当成了很小的值。

**原因**：我给 map 写了 `format=gray`。这条会把 16 位灰度**只读成 8 位**，
于是 3840 范围的坐标被砍到 0~255 —— 采样几乎全落在图像中心附近，
于是呈现放射状拖尾。

**判据实验**（第一步）：

```
恒等映射（xmap=列号、ymap=行号）
  fmt=gray        最大差 255   平均差 109.365   完全相同=False
  fmt=gray16le    最大差   0   平均差   0.000   完全相同=True    ← 逐像素完美
```

**改法**：`[1:v]format=gray16le[x]`。

### 坑 2：map 的数值 = **源图上的像素坐标**

用"坐标即数值"的渐变图做平移测试：map 整体 +10 → 输出的 R 通道跟着 +10
（256 个位置里 247 个吻合，不吻合的 9 个正是被 `fill=black` 裁掉的边界）。
**不是归一化坐标。**

### 坑 3：remap 的**输出尺寸 = 输入尺寸**，与 map 的存储尺寸无关

对照实验：同一份几何，map 分别存成 2048×1024 与 2048×2048：

```
A map尺寸=2048x1024  输出=(1024, 2048, 3)
B map尺寸=2048x2048  输出=(2048, 2048, 3)
前 1024×2048 区域：最大差 0   平均差 0.000
```

**map 的尺寸无关紧要，remap 按逐输出像素一对一取值。**
所以想让输出是 W×H，就要把**源** scale 成 W×H。

### 坑 4：`maskedmerge` **不能用来选路**

它是三输入（A / B / mask），但 mask 是**混合权重**，不是选择器。
用已知图案测出来：

```
A=纯红  B=纯绿
遮罩=white -> 取 [150,150,150]   ← 红绿各半混成灰，不是"取红"
遮罩=black -> 取 [76,76,76]
```

**正确做法**：把遮罩"烘"进图像再相加（全程只用两输入的 `blend`）：

```
A' = A × mask          → [ua][m0]blend=all_expr='A*B/255'
B' = B × (1 − mask)    → [da][m1]blend=all_expr='A*(255-B)/255'
输出 = A' + B'          → [u2][d2]blend=all_expr='A+B'
```

用已知图案验证选择逻辑（第十一步）：

```
左半（遮罩白）像素 [255,0,0]  -> 期望红  对
右半（遮罩黑）像素 [0,255,0]  -> 期望绿  对
```

### 坑 5：ffmpeg 标签名**不能带撇号**

`[a']` 会被解析器当成引号，报：

```
Stream specifier 'a][b' in filtergraph description ... matches no streams
```

改用 `[aa]`、`[bb]` 这类普通名字。**这个报错信息很有误导性** ——
它看起来像"流没接上"，其实是标签里的撇号。

### 坑 6：`blend` 只有**两**输入

三输入会报 `More input link labels specified for filter 'blend' than it has inputs: 3 > 2`。

另外：源要用 `format=rgb24`，**不要**转 `yuv420p` ——
后者有色度子采样损失（恒等映射的平均差会从 0.0000 升到 0.130）。

## 三、决定性判据：与 Python 实现逐像素比对

"看图觉得对"不可靠。所以造了一张**合成鱼眼**（每个像素的颜色直接编码它代表的方向），
同一张图分别交给 ffmpeg remap 与 Python 自己的采样器：

```
合成鱼眼 1024x1024（R=经度 G=纬度 B=半径）
Python 侧输出 (512, 1024, 3)    ffmpeg 侧输出 (512, 1024, 3)
在几何有效区内比对（290816 个像素）：
  完全相同      100.00%
  中位差 0.0   p95 0.0   最大 0
```

**几何公式一致，逐像素 100% 相同。** 这一步把"几何对不对"变成了可测量的量。

再在**真素材**上用最终管线比对：

```
ffmpeg    上/中/下亮度  171.7 / 123.2 / 128.6
Python    上/中/下亮度  171.2 / 122.7 / 128.0
完全相同 12.7%   差<=30 89.7%   中位 5.0   p95 46.0
```

差异来自**插值方式**（Python 是三路双线性 + 兜底，ffmpeg 是单次双线性），
不是几何错。

## 四、管线（`Code/pano360_transcode.py`）

```
[0:v:0] scale=L:L,format=rgb24 ─┐
[1:v]   format=gray16le  ───────┼─ remap ─┐
[2:v]   format=gray16le  ───────┘        │
                                          ├─ blend(A*B/255) ──┐
[5:v] format=gray,format=rgb24 (mask) ────┘                  │
                                                             ├─ blend(A+B) ─→ H.264
[0:v:1] scale=L:L,format=rgb24 ─┐                            │
[3:v]   format=gray16le  ───────┼─ remap ─┐                  │
[4:v]   format=gray16le  ───────┘        │                  │
                                          ├─ blend(A*(255-B)/255) ─┘
[5:v] format=gray,format=rgb24 (mask) ────┘
```

- `L` = 解码后缩到的鱼眼边长（源 3840；默认取 2048）
- map 与遮罩按 `(lens_size, equi_w, fov)` **缓存**，同一套几何只算一次
- 输出 `-c:v libx264 -pix_fmt yuv420p -movflags +faststart` → 浏览器可直接 `<video>` 播放

### 接口

```python
from pano360_transcode import transcode_pano
ok, seconds, err = transcode_pano(src, dst, cache_dir,
                                  lens_size=2048, equi_w=2048, crf=22)
```

命令行：

```bash
python -B Code/pano360_transcode.py <src.OSV> <dst.mp4> --width 2048 --crf 22
```

## 五、性能：瓶颈在哪、硬解有没有用

### 分环节计时（各转 5 秒，同一台机器）

```
基线A：两路 4K 解码 + scale 2048² + 编码      54.0s    0.09x
基线B：单路 4K 解码 + scale 2048² + 编码      25.4s    0.20x
单路 remap（scale+gray16le+remap）           26.8s    0.19x
双路 remap                                  50.7s    0.10x
完整管线（双路 remap + 烘遮罩 + 双 blend + 编码） 76.3s    0.07x
完整管线，不编码（只到滤镜）                    72.4s    0.07x
```

这一轮测量时**有别的进程在抢 CPU**，所以绝对值偏慢；后来又做了一次受控对比
（机器空闲）：

```
单路 -> scale 1280² -> H.264      6.0s    0.84x
单路 -> scale 1536² -> H.264      6.5s    0.77x
单路 -> scale 2048² -> H.264      7.3s    0.68x
两路 -> scale 1024² -> blend     12.4s    0.40x
两路 -> scale 1536² -> blend     16.5s    0.30x
两路 -> scale 2048² -> blend     21.6s    0.23x
```

**结论：主要成本是"两路 4K@60 解码 + 缩放"，不是 remap。**
`remap` 相比"同尺寸的 scale+编码"只多约 5%；编码只占完整管线的约 5%。

### 硬件加速：**驱动装好后可用，但收益意外地小**

用户 2026-10-16 把 RTX 4060 的驱动装好后：

```
设备状态   OK   NVIDIA GeForce RTX 4060 Laptop GPU
           OK   AMD Radeon 780M Graphics
nvidia-smi NVIDIA-SMI 617.42   CUDA UMD 13.4   WDDM   8188 MiB
关键 DLL   nvcuda.dll / nvml.dll / nvEncodeAPI64.dll / nvcuvid.dll  全部就位
```

（装驱动前：设备状态 `Error`、ProblemCode 31、驱动日期 2006/06/21、
`DriverStore` 里只有 `nvhda.inf` 没有 `nv_disp.inf`、`nvcuda.dll` 不存在。）

**生产管线连跑 3 次取中位（5 秒片段，2048×1024）：**

| 配置 | 各次 | 中位 | 实时倍率 | 79 秒素材约 |
|---|---|---|---|---|
| 软解 + 软编 | 28.3 / 28.1 / 26.8 s | 28.1 s | 0.18x | 7.4 分钟 |
| **cuda 硬解 + NVENC** | 24.6 / 25.2 / 27.9 s | **25.2 s** | **0.20x** | **6.7 分钟** |

CPU 时间上收益更明显：软解+软编 303 s → cuda 硬解+NVENC **196 s**（降 35%）。
但**墙钟只快约 10%** —— 因为**重投影与混合才是大头**，解码/编码只占一部分。

**结论：默认用 `hwaccel="auto"`（探到 cuda 就用）+ `encoder="auto"`（NVENC）。**
不指望它带来数量级的提升，但也确实稳赚。

### 硬解的几个坑

1. **`-hwaccel_output_format` 不能写死。** 我一律写 `d3d11`，于是选到 cuda 时
   格式不匹配，输出 `frame= 0`、**一帧都出不来**。要按 hw 名字取
   （见代码里的 `HWACCEL_OUTPUT_FORMAT`）。
2. **`hwdownload` 的格式要按源位深给。** `.OSV` 是 HEVC Main10，解码输出是 p010，
   写 `nv12` 会报 `Invalid output format nv12 for hwframe download`。用 `p010le`。
3. **单看解码能通过 ≠ 全链能用。** `d3d11va` 单独解码没问题（甚至 1.42x），
   接进完整重投影管线却一帧不出。**所以探针的判据要带 remap**，
   而且探针用的 map **尺寸必须与探针里 scale 出来的帧一致**
   （我写成 180×320 对 320×320 源，`remap` 失败，把好端端的 cuda 给误禁了）。
4. **兜底比探针可靠。** 与其把探针写得越来越严，不如让 `transcode_pano()`
   在硬解路径出不来东西时**自动换软解重跑**。已验证：强制指定已知失败的
   `d3d11va`，它会回退并成功产出（耗时里能看到 `[fallback]` 标记）。

### ⚠️ 关于性能测量的诚实说明

我在这个问题上**反复测错**，把教训记下来：

- 同一件事在不同时刻测出过 **0.02x / 0.03x / 0.05x / 0.08x / 0.16x / 0.18x /
  0.19x / 0.20x / 0.23x** 等一堆值。机器上有别的负载（我并行跑的转码任务）
  时，墙钟时间**完全不可信**。
- 我一度据此断言"**瓶颈是 4K HEVC 软件解码**"，后来完整管线稳定复现 0.18~0.20x，
  与那个断言矛盾 —— **该结论已撤回**。
- 换用 ffmpeg 的 `-benchmark`（utime/stime 是进程自己的 CPU 时间）后又发现
  各次测的帧数/线程数不一致，数字之间仍然无法直接比较。
- 两个具体的测量陷阱：
  - **写 `NUL`/`/dev/null` 当输出**会让 ffmpeg 无法推断封装格式而立刻退出，
    计时得到 0.2 s 的**假快**结果。测速必须写带扩展名的真实文件。
  - **同一条文件同时解两路会严重互相拖累**：`-t 5` 精确 300 帧的前提下，
    单路 26 fps、两路 **3 fps**（2 倍工作量掉 8.7 倍速）。

**唯一可信的做法**：固定生产配置，**连跑 3 次取中位**。上表就是这么来的。

### 实际转码速度与体积（可复现）

```
2048×1024 @ 59.94fps，CRF 22，veryfast，cuda 硬解 + NVENC
  5 秒片段    ->  约 25 s     约 0.20x 实时
  79 秒素材   ->  约 6.7 分钟  产物约 267 MB（34 Mbps）
```

用户 2026-10-15 明确：「先追求最优效果，后面要做项目的工程化了再考虑减量、
处理速度、文件大小这些问题的优化」。所以默认取 `lens=2048 / w=2048 / crf=22`。

**要提速的话，优先级**：
1. **降帧率**（源 59.94fps → 30fps）—— 理论上省一半，且不依赖硬件
   （实测里这一项没测出明显收益，但那是被负载污染的测量，值得在空闲时重测）
2. 把重投影也搬上 GPU（`vulkan` / `opencl` 滤镜）—— 因为**重投影+混合是大头**
3. 降 `lens_size`（2048→1536）
4. `preset` 往快调（`veryfast` → `ultrafast`）
