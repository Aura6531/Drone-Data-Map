## 一、照片定位（已完成 ✓）

**已完成** ✓ `Code/photo_meta.py`

- 读 DJI JPEG 的 EXIF（GPS 度分秒）+ XMP（drone-dji 全部字段：云台俯仰/偏航/横滚、
  相对与绝对高度、ImageSource、LensPosition、激光目标点）。**不需要 ExifTool**。
- `ground_target()` 解算「镜头中心点对应的地面位置」（用户要的就是这个点，不是飞机位置），
  三级优先：
  1. 激光斜距 -> `d = 斜距 × cos(俯角)`（最准）
  2. 激光目标高程 -> `h = 飞机绝对高 − 目标绝对高`，`d = h / tan(俯角)`
     （等价于拿到当地真实地面高程）
  3. 平地假设 -> `d = 相对起飞点高 / tan(俯角)`
- **数据质量标签**：走第 3 级的标 `位置不准`（用户明确要求），第 1/2 级标 `实测`；
  每张都带 `accuracy_note` 说明依据。

**实测（Data/ 下 244 张真实照片）**：① 236 张 / ③ 8 张；
解算点与激光实测点平均相距 **0.4 m**、最大 7.2 m。只用平地假设时同一批差 4~16 m。

**界面那层** ✓（2026-10-07 做完，用户 2026-10-06 定的三条决定，照这个做的）：

   > 这条改过两次：一开始是「橙色点 + 外面贴 ⚠ 三角」，2026-10-07 用户说

### 这一轮顺手修掉的五个真 bug（别再踩回去）

1. **后端：`parse_qs` 被当成局部名，打挂了一半的 GET 接口**（`Code/project_manager.py`）
   - `/photo` 与 `/api/project/photos` 里各写了一次
     `from urllib.parse import parse_qs`。Python 只要在函数里看到这个名字是 import 的，
     就把它当成**整个 `do_GET` 的局部变量**；于是同一函数里位置更靠前的那些分支
     （`/api/project/telemetry`、`/api/project/geojson-list`、`/api/project/geojson`、
     `/api/project/get` …）调用它时报
     `UnboundLocalError: cannot access local variable 'parse_qs'`。
   - 文件顶部早就 import 过，把那两行局部 import 删掉即可。
     实测：修之前 `/api/project/telemetry` 返回该错误；修之后 HTTP 200、
     `step=3 count=12181`。
2. **前端：航迹点下标当成遥测下标用**（新增 `telemetryIndexOf`）
   - GeoJSON 的坐标/时间是**逐帧**的（30fps，36542 条），而 `/api/project/telemetry`
     返回的遥测按 `TELEMETRY_STEP=3` **抽稀到 10Hz**（12181 条，`step` 字段写在返回里）。
   - `imagePointOfGround()` / `frameCenterLatLng()` 拿航迹点下标直接读 `tele.alt[i]`，
     读到的其实是第 3i 帧的姿态 —— 偏差随下标线性放大，中段能差 180°。
     后果：「照片目标点是否在画面内」几乎全判错（**147 组里只有 18 组命中**），
     「按位置搜索飞行视频」的 A+B 检索同样受影响。
   - 修法：`telemetryIndexOf(t, tele, i)` **首选按时间对齐**
     （`track.times[i]` 在 `tele.times` 里二分找最近的一条 —— 抽稀是按记录计数，
     SRT 里个别记录缺经纬度会掉，间隔并不严格均匀），`tele.times` 不在时退回
     `step` 整除（测试桩 / 老后端）。
   - 实测修完后：「画面内」命中 **18 -> 100 / 147**（这一档是离线喂遥测算的，
     还没算上第 3 条那个「遥测根本取不到」的 bug；两条都修好之后，
     真实页面自报是 **147/147**，见上一节的实测数据）。
3. **前端：遥测请求的参数一直是错的 —— A+B 检索与照片跳视频双双静默失效**

     `path`（**相对路径，且必须 .mp4/.mov**）。
   - 而 `ensureTrackTelemetry()` 只传了 `path`，传的还是航迹自己的 `fileInfo.relative_path`
     （**它是 `.geojson`**）。于是后端先回「缺少项目名称」；就算补上 name，
     也会回「指定文件不是 MP4/MOV 视频」。**遥测一条都取不到。**
   - 后果（静默、没有任何报错横幅，只是功能退化成「都不在画面内」）：

     * 「按位置搜索飞行视频」的 A+B 检索同样永远拿不到姿态，
       只能退回「无人机位置最近」那条兜底分支（B 分支从上线起就没生效过）。
   - 修法：参数拼装抽成 `telemetryQuery(info, projectName)`（纯函数，好断言），

     缓存键改成「文件夹下标 + 相对路径」。`trackVideoPath()`（照片跳视频用）

     **下次遇到「界面静默失效」，优先用这个方法**（脚本见下面「怎么复现」）。

4. **前端：候选里带的相对路径是 `.geojson`，点「跳视频」直接播不了**
   （`photoMatchesFor` 的 `relativePath`）
   - 用户截图里那条红字是关键线索：
     `path=DJI_20260924101516_0001_T.geojson` —— 播放器的 `path` 尾巴挂着 `.geojson`，
     `/api/project/video` 于是回「指定文件不是 MP4/MOV 视频」，播放器全黑。
   - 原因：候选对象里 `relativePath:String(clip.info.relative_path)`，
     而 `clip.info` 就是航迹的 `fileInfo`，它的 `relative_path` **是 `.geojson`**。
     `video`（按钮上的文件名）来自 `track.video`，那个是对的 —— 所以界面看着一切正常，
     按钮也能点，只有真按下去才炸。
   - 修法：路径统一走 `const videoRel=track.video||videoPathFromGeojson(clip.info.relative_path);`，
     `video` 与 `relativePath` 都用它。
   - 实测（无头 Chrome 抓真实网络请求）：修后发出去的是
     `/api/project/video?...&path=DJI_20260924101516_0001_T.MP4`、
     `/api/project/proxy?...&path=..._T.MP4&start=480&duration=90`；
     播放器 `readyState: 4`、`error: null`。
   - `test_photos.js` 补了断言：用**真实航迹**跑一遍 `photoMatchesFor`，
     检查候选的 `relativePath` 是 `.mp4`、不是绝对路径、且起播秒数
     正好等于「照片时刻 - 视频首帧时刻」。

5. **前端：点某张照片时按「整个文件名前缀」配对，几乎从不命中**
   （新增 `streamTagOf` / `pickMatchForPhoto`）
   - 症状（用户 2026-10-07 报）：点广角照片，跳出来的却是热成像 / 另一路视频。
   - 根因：照片与视频的**序号是各自计数、通常对不上**：
     ```
     照片 DJI_20260924095348_0002_V.JPG  -> 前缀 DJI_20260924095348_0002
     视频 DJI_20260924095258_0001_V.MP4  -> 前缀 DJI_20260924095258_0001
     ```
     原来用 `photoStreamPrefix(视频) === photoStreamPrefix(照片)` 配，几乎从不成立，
     于是全都退回 `matches[0]` —— 那一条是按「画面内 / 时间差」排出来的，
     可能是 S 或 T。**实测 244 张里 189 张跳错。**
   - 修法：抽 `streamTagOf(name, ext)` 取末尾流标识（`_V` / `_T` / `_S`），
     `pickMatchForPhoto(matches, name)` 三级优先：
     ① 同一路（`_V` 配 `_V`）→ ② 同一架次（时间戳一致、序号不同也算）→ ③ 排序最好的那条。
     `openPhotoVideo` 与它的「还没匹配」兜底路径都用这个函数（原来兜底直接跳 `fresh[0]`）。

## 二、`LRFStatus` 的实际情况（已查清，别再猜）

M4T 照片实测**只有两个取值**：

| 取值 | 含义 | 伴随数据 |
|---|---|---|
| `Normal` | 测距有效 | 一定有斜距 + 目标经纬度 |
| `TooFar` | **无有效回波** | 没有斜距/目标点，其它字段残留 **0.0** |

**`TooFar` 不是"目标太远"** —— 实测那 8 张的估算距离只有 47~190 m。
结合画面判断：**失败的都是水（镜面反射，斜入射收不到回波）**；
对照组是一张打在浮标上的水面照（俯角 -51.4°，近垂直 + 固体目标）= `Normal`。

**判据必须用 `LRFStatus == "Normal"`** ✓ —— 只看距离字段会踩坑：
`TooFar` 时 `abs_alt=0.0`，拿它当"当地地面高程"会让落差从 56 m 变成 69.7 m，
中心点偏出约 30%。

## 三、平地假设的适用边界

俯角越平，误差放得越大。建议按俯角决定是否采信：

- 俯角 ≥ 45°：平地假设可用；
- 俯角 20°~45°：偏大，交付时带 `位置不准`；
- 俯角 < 20°：误差可达百米级，**必须人工核对**。

**这 8 张 `位置不准` 的照片**（都在 `Data\DJI_202609241014_002\`，供将来核对）：

```

DJI_20260924102746_0034_T.JPG / _V.JPG      俯角 -19.8°   估算 171.5 m   ← 最需要人工核
DJI_20260924103211_0055_T.JPG / _V.JPG      俯角 -33.7°   估算 92.7 m
DJI_20260924103415_0071_T.JPG / _V.JPG      俯角 -18.0°   估算 190.4 m   ← 最需要人工核
```

**将来接 DEM 或手工指定平均地面高程**：接口已留好 ——
