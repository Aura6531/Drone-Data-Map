## 三、发现并修复的 bug：低太阳角下北向算错 ⚠️

### 症状

贡嘎那 8 段的北向结果**看起来很"正常"**（都过了原有的两道可信检查），
但数值可疑：

```
素材                     north_yaw   日面r/R   预期r/R   日面px
贡嘎 …071803_0004_D       +30.97     0.8877    0.8993    17509   ← 面积是正常的 5 倍
贡嘎 …072911_0006_D       -14.41     0.9030    0.8764     7991
贡嘎 …072720_0005_D       -21.16     0.9020    0.8800     8014
（对照：10-14 那批        -139.21     0.4534    0.4716     2664）
```

**日面半径 0.89~0.91 vs 正常的 0.45~0.48；面积 17509 px vs 正常的 2000~3600 px。**

### 定位：把日面标出来看

标注图 `_sun_04_D.png` 一眼就能看出：**红圈套在一条橙色的地平线亮带上**，
日面根本不在画面里。画面上方是雪线，天空是渐变 —— 这是**刚日出**的场景。

查理论太阳高度角，原因就清楚了：

| 素材 | 太阳高度角 |
|---|---:|
| `DJI_001` 10-14 两段 | +41.39° / +42.84° |
| `DJI_001` 10-15 下午两段 | +47.06° / +46.75° |
| **贡嘎 …071803_0004_D** | **+0.07°** |
| **贡嘎 …072911_0006_D** | **+2.45°** |
| 贡嘎 …073912_0007_D | +4.58° |
| 贡嘎 …074052_0008_D | +4.94° |
| 贡嘎 …074144_0009_D | +5.12° |
| 贡嘎 …075758_0001_D | +8.55° |

**太阳贴着地平线** → 整个天空是一大片渐变的晨昏光带 →
"找最亮区当太阳"**必然**抓到光带。

### 为什么原有的两道检查拦不住

原来的可信度检查是：

1. 日面必须落在"由太阳高度角预测的半径"±0.06 内
2. 过曝块必须 **≥ 800 px**（防"太小的碎片"）

**两道都是防"太小/位置不对"的**。而地平线光带**又大又亮、位置也接近预测半径**
（因为太阳本来就在地平线附近，预测半径自然大）—— 正好从"过大"这一侧钻过去了。

### 修法（三道）

| 层 | 改动 |
|---|---|
| `pano360_north.MIN_SUN_ELEVATION_DEG = 12.0` | **物理前提**：太阳高度角低于 12° 就直接判不可用，不量 |
| `pano360_service` | 日面面积改成**区间** `800 <= blob <= 8000`（挡掉 17509 px 的光带） |
| `pano360_service` 失败文案 | 把**真实**原因说出来，不再一律怪"水面反光" |

> **为什么门槛是 12°**：低于它时，日面与地平线光带的角距离已经进入容易混淆的区间；
> 高于它，日面稳稳落在天空里（实测 +41° 那批两次独立测量一致到 0.02%）。

### 修完之后

```
DJI_001 10-14 两段        -28.78 / -139.21      OK  日面 2822 / 2664 px
DJI_001 10-15 下午两段    +165.43 / -179.40     OK  日面 1621 / 3648 px
贡嘎 8 段                 全部留空              "太阳高度角只有 +0.07°（低于 12°），
                                                太阳贴着地平线，无法可靠地把日面和
                                                地平线光带分开 —— 北向留空，不猜。"
```

**宁可返回"不可用"，也不给一个错的方向** —— 错的方向比没有方向更危险。

## 四、查过但**确认正常**的两件事

### ① 负的相对高度是**正常**的（山顶起飞）

> 用户 2026-10-15 指出：「贡嘎的第三个视频是来回飞行录制的，因为是**山顶起飞**，
> 起飞点高度 0m（非海拔），然后有些片段是飞到了**山顶的侧下方**，高度为负值。
> 这个是正常情况，换算成海拔就没问题了。」

**用户说得对，而且量出来的数据比预期还干净。** 我原来那句"飞进深谷了"是**我猜的**，
不准确 —— 准确的说法是"飞到了起飞点下方"。

核实：`abs_alt − rel_alt` 就是**起飞点海拔**，是个常数。12 段素材全部测下来：

```
偏移（abs_alt − rel_alt）的标准差 ≤ 0.0005        ← 极稳
起飞点海拔：DJI_001 那批   3473.0 / 3541.7 m
            贡嘎         4530.3 / 4876.2 / 4934.9 m   ← 山顶起飞
```

所以 `rel_alt` 与 `abs_alt` **只差一个基准**：`rel` 以起飞点为 0，`abs` 是海拔。
负值完全正常：

| 素材 | 起飞点海拔 | rel_alt 最低 | abs_alt 最低 |
|---|---:|---:|---:|
| `贡嘎 …075758_0001_D` | 4934.9 m | **−108.7 m** | 4826.1 m |
| `DJI_001 …142247_0002_D` | 3541.7 m | −20.8 m | 3520.9 m |
| `DJI_001 …142002_0001_D` | 3541.7 m | −7.0 m | 3534.7 m |

**做出来的东西**：`load_srt_telemetry` 现在多给两个字段 ——
`alt_abs`（海拔）与 `takeoff_elev`（起飞点海拔），
这样界面上就能把高度讲清楚，不必让用户自己换算。

`Code/test_altitude_reference.py`（已登记）把这个不变量钉住了。

### ⚠️ 但这件事暴露了覆盖几何的一个**真局限**

覆盖的圆环半径 = `h / tan(仰角)`，这里的 `h` 要的是**离地高度（AGL）**。
而 `load_srt_telemetry` 的 `alt` 用的是 `rel_alt` —— 它其实只是**离起飞点**的高度。

平坦地形上两者差不多；但在**山顶起飞、飞到侧下方**时就不一样了：

- `rel_alt` 为负 → 现在被 `alt <= 0` **直接跳过**
- 可是那个位置的**离地高度可能仍是正的**（地形在它下面）

实测影响：`贡嘎 …075758_0001_D` 有 **2110 / 10651 帧（20%）** 因为这个被跳过。

**要正确处理需要有 DEM（地形高程）：`AGL = abs_alt − 该点地面高程`。目前没有 DEM，
所以只能保守跳过。** 这是已知局限，已记在测试与本文档里。

### ② 有 275 帧在建网格时被跳过

原因：那 275 帧的 `alt <= 0`（−7.00 ~ 0.00 m），是**起飞/降落段**位于起飞点以下。
覆盖几何的 `alt <= 0` 分支**正确地排除了它们** —— 高度不为正就算不出足迹，
硬算会得到负高度的错误覆盖。

（注：与上面那条局限是同一个机制的两面 —— 排除是对的，但山地场景下会连
"飞到侧下方"的有效帧一起排除掉。）

## 五之二、**承重更正**：贡嘎那两趟是两个完全不同的东西

> 用户 2026-10-15 指出：「贡嘎的两个视频是悬停的，拍摄长时间的延时摄影，
> 经纬度不动很正常」。
>
> 这一句让我回去重查，结果发现**我上一版文档写错了**，而且错得不止一处。

### 错在哪

我原来写的是「贡嘎多段位移极小（有的整趟只有 11 个唯一坐标、跨度 3e-7° ≈ 3 cm）
→ 是真的基本悬停」。**这个数字是错的**：我的遍历步长与 `parse_dji_srt` 返回的长度
不匹配，**只采到了很小一段**，于是把一整趟真航线看成了"没动"。

用正确的全量采样重算之后：

| 素材 | 离起飞点最大水平距离 | 高度（rel_alt） | 真相 |
|---|---:|---|---|
| `贡嘎 …071803_0004_D` | **0 m** | 118.6 ~ 120.1 m（494 s 只变 1.4 m） | **纯悬停延时** —— 正是用户说的那种 |
| `贡嘎 …075758_0001_D` | **1110 m** | −101 ~ +127 m | **一趟真飞的航线**（东南 → 东北 → 西北 → 回原点），不是悬停 |

也就是说：**用户说的"悬停"对 `0004` 完全成立，但 `0001` 不是悬停**，
而我把两趟混为一谈、还用了个错误的数字去论证。

### 修正后的判断

- `0004` 这类**纯悬停延时**：位置钉死 → 覆盖就是**一个稳定圆盘**（半径
  `max(600, 12×118.6) = 1423 m`）。这是几何上的正确结果。
  高度稳定也说明它的遥测可信。
- `0001` 是**真航线**，它那 −101 m 的下探与 +127 m 的爬升是飞行本身
  （高度与水平距离的相关系数 **−0.08**，也就是各飞各的，不是随地形走）。
  它的覆盖是一大片扫过的区域（1141 公顷）。

### 教训 → 做成了自动判据，不再靠眼看

**"位移很小"必须量准，不能凭一段采样下结论。** 所以这个判断现在由代码算，
判据是 **水平位移跨度 / 高度跨度**（`pano360_coverage.flight_profile()`）：

| 情况 | 判据 |
|---|---|
| 高度跨度 ≤ 3 m | 只看水平漂移：≤ 30 m 算 hover，否则 transit |
| 高度跨度 > 3 m | 比值 ≤ 0.5 算 hover，否则 transit |

实测标定（`Code/test_flight_profile.py`，已登记进 `run_tests.js`）：

```
素材                       判定        水平漂移    高度跨度    比值    时长
贡嘎 0004（真悬停延时）      hover         0.4 m    10.6 m   0.04   494.8s
贡嘎 0001（真航线）         transit    1109.5 m   140.3 m   7.91   533.3s
```

全 12 段跑一遍的结果（`/api/pano360/list` 里每条都带 `profile`）：

```
DJI_001 那 4 趟         transit   漂移  162 ~ 1391 m
贡嘎 7 趟                hover     漂移  0.1 ~ 10.8 m     ← 用户说的悬停延时
贡嘎 0001               transit   漂移 1109.5 m          ← 我上一轮看错的那趟
```

**所以用户对素材的判断是对的**：贡嘎绝大多数确实是悬停延时。
但 `0001` 不是 —— 而它恰好是我原来"依据一个错误数字"论证过的那趟。

（另：`0001` 那 2110 个被 `alt <= 0` 跳过的帧，是它真下探到起飞点以下的那些，
排除是对的。）

## 七、已知遗留

- **贡嘎 `…075758_0001_D` 建网格耗时 521.9 s**（vs 另两段 11.4 / 43.4 s）。
  它 8541 帧有效、网格 4540×3708。慢的原因是 `_raster_sphere_ring` 逐行扫
  整张网格的列区间。**可用但偏慢**，如果这批素材要常用，值得优化
  （例如先按行的距离范围裁出列区间，而不是每行扫全宽）。
