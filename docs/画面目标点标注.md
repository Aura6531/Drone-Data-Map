# 画面里的目标点标注（2026-10-13）

> 需求（用户）：
> **「地图上所选的位置点，应该在画面当中给我标注出来」**

## 一、它和已有的「画面中心准星」不是一回事

| | 画面中心准星（已有） | **目标点标注（本次）** |
|---|---|---|
| 位置 | 永远在画面正中 | **跟着目标跑**，随飞机移动/云台转动在画面里移位 |
| 颜色 | 青绿 `--reticle`（变焦时转红） | 玫红 `#f43f5e` + 脉冲 + 标签 `Your point` |
| 含义 | "画面中心对着哪里" | **"你在地图上点的那个点在画面里的位置"** |

两个都要留 —— 准星帮你判断构图，标注帮你确认"我要看的东西在不在画面里、在哪个位置"。

## 二、实现

### 复用了已有的投影函数

页面里本来就有 `imagePointOfGround(track, telemetry, i, latlng)` ——
它是给结果卡算"目标在画面哪个方位"用的（"top right" 那些字）。
**没有另写一套投影**：新增的只是"把它的结果摆到 DOM 上"。

```js
const p = imagePointOfGround(clip.track, telemetry, i, probeLatLng);
el.style.left = ((p.xImg + 1) / 2 * 100) + '%';
el.style.top  = ((1 - p.yImg) / 2 * 100) + '%';   // ← y 要翻
el.hidden = !p.visible;
```

**两个最容易错的地方：**

1. **y 轴方向** —— 图像 y 向下、而 `yImg` 向上为正，不翻就上下颠倒。
   测试里专门钉了这条（正下视时北侧目标应落在 top < 50%）。
2. **画面外必须隐藏** —— 不能让标记贴在边缘误导人。
   `p.visible === false`（目标超出视场）或 `p === null`（在相机背后）都隐藏。

### 接入的五个时机

| 时机 | 为什么 |
|---|---|
| 每帧遥测更新（`syncDroneMarker` 尾部） | 标记要跟着画面走 |
| `setProbe()` | 换了选点立刻更新 —— 否则"选了新点但画面里还是旧标记"，看着像没生效 |
| `clearProbe()` | 选点没了就收掉 |
| 遥测加载完成 | 打开视频那一刻就该出现（这时才知道相机姿态） |
| `closeVideo()` / `boot()` | 视频关了收掉；启动时初始化 |

### 索引复用页面已有的 `telemetryIndexAt()`

第一版我另写了一个按 `videoPlayer.currentTime` 二分的版本 —— 删掉了。
页面里本来就有 `telemetryIndexAt(clip.trackSeconds)`，**两套索引逻辑迟早会不一致**。

## 三、测试 `test_target_marker.js`

它**把页面里的 `imagePointOfGround` 抠出来在测试里跑**（不是照抄一份），
所以验的是页面真正在用的那段代码：

```

北侧目标在画面上方且可见（yImg > 0） -> yImg=0.750
北侧目标的 top% 落在 0~50（y 轴翻对了） -> 12.5%
东侧目标在画面右方（xImg > 0） -> xImg=0.391

目标不可见 -> 隐藏标记
没选点 / 没视频 / 没遥测 -> 隐藏
代码里用的是模块级 telemetry（不是 clip.telemetry）
```

> 写这个测试时自己踩了两个坑，都值得记：
> **① 注释里也写了 `clip.telemetry`**（用来解释"为什么不用它"），
> 所以"代码里不许出现 clip.telemetry"这条断言必须先跳过注释行。
> **② 第一版"北侧"用例偏了 55 m** —— 高度 100 m、垂直视场 47.68° 时
> 画面只覆盖南北约 ±44 m，**偏 55 m 已经出画面了**，
> 拿一个 `visible=false` 的点去断言"在画面上方"当然失败。
> 换成偏 33 m 才落在画面内（yImg=0.750）。

## 五、顺带修掉的：命中帧在视频开头时"一开播就停"

用户同一次反馈里报的：

> **「当我点检索里面的这个图片的时候，不会播放 3 秒然后自动暂停。
> 看看是不是因为刚刚起飞，3 秒前还没有开始录制的原因？其他图片都是 3 秒后自动暂停的。」**

**猜得完全正确。** 那张卡的命中帧是 `t=0.0s`（帧 0，刚起飞那一帧）：

```
jumpToFrameHit():  from = max(0, 0 − 3) = 0     ← 倒不出 3 秒，起播点被夹到 0
                   photo_pause_at = target = 0  ← 暂停点也是 0

tickPhotoPause():  if (currentTime >= photoPauseAt − 0.02)
                   → 0 >= −0.02 立刻成立 → 一开播就 pause()
```

所以表现是"**瞬间停在第 0 帧**"，看着像播放坏了，而不是"到点自动停"。
其他卡片的目标时刻在 20 分钟处，有 3 秒余量，所以正常。

### 影响面（实测 5 个位置、两个档位、24 条命中）

只有 **2 条**是这种情况（同一个点、两个档位各一条），而且都是 `t=0.0s`、
起飞爬升段（俯角仅 −17.4°、18.5 cm/px）—— **判读价值本来就低**。

### 修法

**余量不足时不设暂停点**（`0` = 不暂停），让它正常播，并在标题里说明原因：

```js
const hasLeadIn = target >= PHOTO_PREROLL_SECONDS;
photo_pause_at: hasLeadIn ? target : 0,
pause_has_lead_in: hasLeadIn,
```

`setPhotoCountdownTarget()` 增加 `hasLeadIn` 参数，为 `false` 时清掉暂停点
（不这样做的话，`photoPauseAt` 仍是 0，还是会瞬间停）。

标题相应变成：

```
Playing DJI_…_0001_V from 00:00.000, no lead-in before 00:00.000 —
this frame is at the very start of the recording, so it plays on instead of
pausing (18.5 cm/px)
```

### 为什么不做"换个位置重播"那种复杂方案

考虑过"倒不出余量时改从后面几秒播、再绕回来"。不做：

1. 影响面只有 2 条、且都是低价值的起飞帧
2. 会让**暂停点 ≠ 缩略图那一帧**，用户点击的期待就是"看到那一帧"
3. 那一帧本来就在起播位置上，**不会错过**

> **推翻了一条旧注释**：代码里原写着"只要有目标时刻就一定要停，
> 不能写成 `from<target ? target : 0`"。那条注释解决的是"一路播下去、停不在那一帧"，
> 但引入了"开头帧一开播就停"这个更糟的表现。
> 现在按"**够不够余量**"分情况，测试也相应改了口径。
