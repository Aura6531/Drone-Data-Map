# 四个产品方向的评估（工作量 / 可行性 / 流程）

> 写于 2026-10-12。基于**当前这份代码的真实状态**评估，不是泛泛而谈。
> 结论先给：**先做「第 1 方向 + 第 4 方向」的公共底座（一个数据索引），
> 再按客户类型选第 3 或第 2 分支。** 理由见文末「五、建议的推进顺序」。

---

## 一、今天的代码到底是什么（评估的地基）

| 事实 | 数值 / 位置 | 对后续方向的含义 |
|---|---|---|
| 纯标准库 | `project_manager.py` 无第三方依赖（无 flask/fastapi），`ThreadingHTTPServer` | 轻、好打包；但要扛多用户/高并发就得换或加东西 |
| 项目状态是 **JSON 文件** | `Project/<项目名>/project.json` | 单机够用；多人同时写会互相覆盖（**方向 2 必须先换存储**） |
| 数据是**按目录扫描**，无索引 | `scan_folder()` 现扫现用；`Data/` 不进仓库 | 数据一多就慢；跨项目检索没有入口（**方向 1、4 的核心缺口**） |
| 检索是**逐点线性扫** | `nearestPerStream()` 遍历每条航迹的每个点 | 几万点很快；几十万条航迹就要空间索引（R 树/网格） |
| 遥测内存缓存上限 24 条 | `TELEMETRY_CACHE_MAX = 24` | 多用户并发取遥测会反复解 SRT |
| 转码缓存 4 GB / 导出 2 GB / 瓦片 2 GB | `PROXY_CACHE_MAX_MB` 等 | 磁盘会被缓存吃掉，多用户场景要重新算账 |
| 地图瓦片**只能现取现缓存** | `proxy_map_tile()` + `tile_cache/`（7 天） | **方向 2 的硬骨头**：内网没有外网就取不到瓦片 |
| 出站访问是**服务端代取** | 瓦片/地名/逆地理都走后端 | 好处：前端不用管 CORS 和内网白名单 |

## 二、四个方向各自的真实工作量

### 方向 1：单机化数据管理软件（家庭 / 个人）

**可行性：★★★★★ 最高。** 现有形态已经是个单机软件，缺的是「管很多数据」的能力。

要做的事：

1. **数据目录索引（必需）**
   - 启动时（或定时）扫描若干「数据根目录」，把每个 DJI 素材登记进一张表：
     `架次 / 拍摄时刻 / 机型 / 视频类型 / 坐标范围 / 时长 / 是否已有 SRT / GeoJSON / 缩略图`
   - 存放位置已定：数据目录下一个 SQLite（`uav_index.db`），别再用 project.json 存清单。
2. **跨项目的统一视图（这是「存到一起」的意义）**
   - 一张地图看**所有**架次的覆盖范围（现在的热力图/覆盖分析就是雏形）
   - 按日期 / 地点 / 机型 / 关键词筛，而不是先进项目再看文件
3. **导入流水线更省心**：拖入整个硬盘目录 → 自动识别架次 → 批量补 SRT/GeoJSON（现在的全自动流水线扩展成后台任务 + 进度）
4. **去重与整理**：同一架次的多份拷贝、剪辑版、改名文件
5. **打包**：现在已有 `packaging/`（PyInstaller + 自带向导安装程序），这条路基本已铺好

**工作量：2–4 周**（一个人）。没有架构性风险，全是工程活。
**风险点**：硬盘上几十万文件时的扫描速度 —— 用 SQLite + 文件 mtime 增量扫描可解。

---

### 方向 2：内网局域网数据平台（政企 / 交付）

**可行性：★★☆☆☆ 最低，但**单价最高、最像「产品」。它要动的是**架构**，不是功能。

必须补的：

| 缺口 | 现在 | 需要 |
|---|---|---|
| 多用户 | 无登录 | 账号 / 角色 / 项目级权限（谁能看哪个项目） |
| 并发写 | project.json 整文件读写 | PostgreSQL（项目、架次、标记点、用户） |
| 元数据 | 目录扫描 | 索引库 + 任务队列（导入/转码/生成轨迹都是后台作业） |
| 大文件 | 本机路径直读 | 对象存储或 NAS 挂载 + Range 服务（现在有 `send_file_range`，可复用） |
| **内网地图** | 现取天地图/OSM | **离线瓦片**：要么预下载（自建瓦片服务），要么内网部署墨卡托瓦片包 |
| 部署 | 双击 bat | Docker Compose（web + postgres + 瓦片服务 + 作业进程） |
| 交付 | — | 安装手册、备份/恢复、升级方案、验收脚本（现在有 `accept_packaged_app.py` 的基础） |

**工作量：1.5–3 个月**（含 Docker 化、权限体系、离线瓦片）。
**最大不确定性是离线瓦片**：政企内网通常有内网地图服务（ArcGIS/超图/自建 WMTS），
那就要做「可插拔瓦片源」；如果没有，预下载全国 15 级的瓦片是**几百 GB~TB 级**，得先跟客户确认。

**这个方向卖的不是软件，是「交付能力」**（部署 + 数据迁移 + 运维）。收入模型通常是项目制。

---

### 方向 3：完全上云 + 集成司空 2 之类的平台

**可行性：★★★☆☆ 技术上不难，难在「谁的生态」。**

要做的事：

1. **数据上云**：对象存储（视频是大头，几百 GB/项目）+ CDN 或预签名 URL
2. **计算上云**：转码/生成轨迹改成异步作业（云函数或容器），现在的同步 ffmpeg 思路要改
3. **身份**：如果接司空 2，就是走大疆的开放平台（OAuth、机构/设备模型、航班数据接口）——
   能不能拿到**原始视频和 SRT**是关键，拿不到就只剩「地图对齐」这一层价值
4. **底图**：云上最容易的一块，天地图/Mapbox/Esri 随便配

**工作量：1–2 个月**（自建云版），**接入司空 2 取决于其开放程度，可能 2 周也可能走不通**。
**风险**：等于是给别人的平台做插件，产品命脉在对方手里；且视频流量成本要算清楚
（一次回放 = 几十 MB，按分钟计费会很难受）。

---

### 方向 4：后台数据库 API 化，给 AI 智能体做自然语言检索

**可行性：★★★★☆ 技术风险低，价值密度高 —— 而且你现在的代码已经具备 70% 的条件。**

先说清楚这件事**为什么现在的项目特别适合**：

- 后端**已经是 HTTP API**（`/api/project/*`），天然就是「工具接口」；
- 数据里已经有**坐标 + 时刻 + 姿态 + 照片位置**（这正是 AI 检索需要的语义锚点）；
- 已经有**出图能力**（`/api/snapshot` 抽帧、`/api/mapsnapshot` 拼地图、报告里的标点），
  「给我几张对应位置的截图」这条需求**今天就能实现**。

#### 一个具体请求会怎么走

> 「我记得之前飞过东莞的东江边，桥头镇那一块，但忘记是哪天了，想要找一下那个河道交汇口的数据情况，检索之后告诉我，并且给我几张对应位置的飞行截图」

```
① 意图拆解（Agent 侧，不用我们写）
   地点=桥头镇/东江边  时间=不确定  目标=河道交汇口  产出=说明 + 截图

② 地名 → 坐标（我们提供工具）
   tool: geocode("桥头镇") -> 经纬度 + 范围框
   （复用现有 /api/geocode 和 test_report.py 里的逆地理）
   注意：AI 可能给模糊地名 → 要能返回「候选几个 + 各自范围框」让它自己挑

③ 查飞行记录（我们提供工具，需要一个索引）
   tool: find_flights(bbox, time_range=null, text=null)
   -> [ {架次ID, 日期, 机型, 时长, 覆盖该框的航迹长度, 最近点距离} … ]
   排序给 AI：覆盖越全、越接近框中心越靠前

④ 空间检索（我们提供工具）
   tool: search_track_points(bbox) -> 命中点 + 时刻 + 高度 + 视频文件
   现在 nearestPerStream 是「一个点找一帧」；这里要反过来「一个框找多段」

⑤ 取证据（我们提供工具）
   tool: get_frames(flight, time, count) -> 视频抽帧（已有 make_video_snapshot）
   tool: get_map_image(lat, lng, zoom) -> 地图截图（已有 make_map_snapshot）
   tool: get_photos(bbox, time) -> 该位置的原始照片（已有 /api/project/photos，
         而且照片带准确的目标点坐标 —— 这比视频帧更适合当"证据"）

⑥ AI 汇总：把 ③④⑤ 的结果拼成人话 + 附图
```

#### 要补的东西（按优先级）

1. **一张索引表**（与方向 1 共用！）：架次、时间、机型、坐标范围、航迹摘要、照片位置
2. **空间查询**：`bbox × 时间` 的 SQL 查询（SQLite 的 R-Tree 扩展就够，不用上 PostGIS）
3. **AI 友好层**（关键，也是最容易被忽略的）：
   - **工具描述要写好**：每个接口的参数含义、单位、返回结构要能让模型自己判断怎么调
   - **返回要「带出处」**：每个结论都附 `架次ID + 时刻 + 坐标 + 文件路径`，
     否则 AI 会编（**这条是这个方向成败的关键**）
   - **别返回大 blob**：轨迹几万个点不能直接塞给模型 → 返回**摘要**
     （范围框、密度、关键拐点），要细节再单独取
   - **幂等 + 明确错误**：失败要返回「为什么失败、下一步可以试什么」
4. **鉴权与配额**：给 Agent 的 key 不能等于全库读权限（尤其方向 2 场景）

#### 这个方向的三种落地形态（可以先粗后细）

| 形态 | 做法 | 工作量 |
|---|---|---|
| A. 只读工具包 | 在现有 API 上加 `bbox`/`time`/`text` 参数 + OpenAPI 描述 | 1–2 周 |
| B. 本地 MCP 服务 | 包一层 MCP（Model Context Protocol），让 DSH/Claude 直接挂载 | +1 周 |
| C. 常驻索引服务 | 后台常驻扫描 + 索引 + 语义检索（向量库可选） | +3–4 周 |

**建议从 A 起步**：不动架构，先让「按位置/时间找数据 + 出图」变成 AI 能调用的工具，
用真实提问打磨返回结构，再决定要不要上 B/C。

## 三、四个方向的关系（不是四选一）

```
                  共同底座
        ┌──────────────────────────────┐
        │  数据索引 (SQLite)            │  ← 方向 1 要它，方向 4 更要它
        │  架次 / 时间 / 范围 / 缩略图   │
        └──────────────┬───────────────┘
                       │
      ┌────────────────┼────────────────┬─────────────────┐
      ▼                ▼                ▼                 ▼
  方向1 单机      方向4 AI 工具层    方向3 云           方向2 内网
  （本机 UI）    （只读 API）      （对象存储+异步）   （多用户+权限+离线瓦片）
      轻              轻                中                 重
```

- **方向 1 和 4 共用同一张索引**：一个给它做界面，一个给它做接口。
  先做索引 = 两个方向同时推进。
- **方向 2 是方向 1 的「重型版」**：把本机路径换成服务端存储、把单用户换成多用户。
  如果先做 1，2 就是「加存储层 + 权限层」，不是重写。
- **方向 3 是方向 2 的「云化版」**，但多了一个生态依赖（司空 2 的开放程度）。
- **方向 4 可以叠加在任何一种上**：本机、内网、云都可以暴露同一套 AI 工具。

## 五、建议的推进顺序

**第 0 步（两周，立刻见效）：做数据索引。**
一张 SQLite：扫目录 → 登记架次（时间/机型/范围/时长/有无 SRT/GeoJSON/缩略图）。
对方向 1 是「管起来」，对方向 4 是「查得到」。**这一步做完，两个方向都算是开工了。**

**第 1 步（两周）：把检索接口变成 AI 可用的工具。**
- 加 `bbox + time + text` 查询，返回**摘要 + 出处**
- 复用已有的抽帧/地图截图/照片接口做「取证据」
- 先在本机用真实提问试（例如你上面那句东莞的），看返回能不能支撑 AI 说人话

**第 2 步（按客户选分支）：**
- 面向个人 → 做方向 1 的界面（统一地图、批量导入、去重）
- 面向政企 → 开始方向 2：先换 PostgreSQL，再做权限，**并行去谈离线瓦片方案**
- 想上云/接司空 → 先做**技术验证**：拿一个真实账号，确认能不能取到原始视频 + SRT。
  拿不到就别做（只剩地图对齐，价值不够）

**不建议现在做的：**
- 直接上方向 2（架构重、周期长、且离线瓦片没确认前有返工风险）
- 直接上方向 3 的完整云版（在没验证司空开放度之前）

## 六、几个具体的技术选型建议

| 问题 | 建议 | 理由 |
|---|---|---|
| 索引用什么 | **SQLite + R-Tree** | 单机/内网/云都能用；几十万架次够；不用运维 |
| 什么时候换 PostgreSQL | 出现「多人同时改同一项目」时 | 那是方向 2 的门槛，不是现在的痛点 |
| 空间检索 | bbox 先粗筛（R-Tree），再精确算 | 和现在 `nearestPerStream` 的精确计算复用 |
| 语义检索（"河道交汇口"） | 先不做向量库 | 先用「地名 → 坐标 + 标签」；真需要再上 |
| AI 接入方式 | 先 OpenAPI/普通 HTTP，再考虑 MCP | 不锁定某一家 Agent |
| 视频上云 | 先算流量账 | 一次回放几十 MB，按量计费很容易超预算 |
